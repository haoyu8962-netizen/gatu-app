# 钱包初始化与本地预览环境

## 已复现的故障

2026-09-11，在本机 Codex 内置浏览器打开 `http://localhost:3006/trade/ARB?scope=all`，
邮箱身份已显示，行情持续更新，但钱包目录未就绪，账户模式、余额、持仓与委托无法加载。
独立排查标签页在未修改应用代码、未注入网络故障的情况下复现了相同状态。

网络记录区分了三类请求：

| 请求 | 结果 |
| --- | --- |
| `https://auth.privy.io/api/v1/apps/<app-id>` | HTTP 200 |
| `https://auth.privy.io/api/v1/sessions` | HTTP 200 |
| `https://auth.privy.io/apps/<app-id>/embedded-wallets`，类型 Document | `net::ERR_BLOCKED_BY_CLIENT`，`blockedReason: other` |

最后一项是 Privy 的隐藏钱包 iframe。它被浏览器客户端拦截，不能把这次失败归因于
Hyperliquid 余额接口、账户没钱、签名钱包地址不匹配或 Vite 依赖缓存。

只读核对当前安装的 Codex 客户端请求处理逻辑确认：本地页面请求非本地子框架时，
客户端会根据浏览器控制状态取消该请求。普通 HTTPS API 请求不属于这个子框架规则，
所以邮箱登录和行情可同时正常。控制状态与 iframe 请求时机不同，也解释了刷新可能
恢复而后续重新进入又失败的现象。这是本次安装版本的行为，不推断所有版本或其他
内置浏览器都有同样限制。

同一开发服务器在独立 Chrome 中已完成钱包初始化，显示已有连接地址与存款入口。
Chrome 使用自己的既有钱包会话，并未迁移内置浏览器中的邮箱凭证；这项对照验证了
浏览器加载链路，不声称验证了同一邮箱在 Chrome 中的交易或签名。
桌面重载与 `393 × 852` 移动视窗重载均完成初始化，钱包菜单可用，未再出现
“连接钱包查看仓位”的占位。测试结束后已移除临时移动视窗设置，未提交订单或签名。

## 为什么会一直等待

项目锁定的 `@privy-io/react-auth@3.30.0` 的 `useWallets().ready` 同时依赖外部连接器、
初始用户解析、iframe 钱包代理，以及用户已有嵌入式钱包的连接结果。邮箱认证就绪
不等于钱包代理就绪。SDK 的 iframe 失败回调没有重新加载 iframe 的恢复处理；
检查过的 3.42.0 发布包保留了这一处理，因此不能把单纯升级当成这次拦截的修复。

应用的 `useWalletSession` 在钱包未就绪时不发布可用交易连接。这个保护仍须保留，
不能把邮箱已登录、超时或旧余额当作钱包已连接。现有 30 秒后的手动重新加载入口
是恢复入口，不保证能消除浏览器持续实施的拦截。

参考：[Privy 连接钱包与就绪状态](https://docs.privy.io/wallets/wallets/get-a-wallet/get-connected-wallet#waiting-for-wallets-to-be-ready)。

## 本地开发入口

未启动服务器时，运行：

```bash
pnpm dev:browser --port 3006
```

该命令运行同一个 Vite 开发服务，并通过 `--open` 打开系统浏览器；`--strictPort`
保证端口被占用时退出，不静默改用其他端口。系统默认浏览器应为 Chrome、Safari
等独立浏览器。若 3006 已有服务器，直接在独立浏览器打开已有 URL，无需重启、
删除 Vite 缓存或再次启动服务。

内置预览可以用于行情和视觉布局检查；真实钱包初始化、邮箱登录恢复、资金与
签名入口的验证须在允许必要 iframe 的独立浏览器中完成。浏览器之间不会共享
登录会话，测试同一账户时由用户正常登录，不复制令牌、密钥或浏览器存储。

## 再次出现时如何判断

1. 在刷新前保留网络记录，分别检查认证 API、钱包 iframe、Vite 模块与账户订阅。
2. 若 iframe 是 `ERR_BLOCKED_BY_CLIENT`，先对照独立浏览器；若两者都有此错误，
   继续检查实际的浏览器拦截来源，不能直接认定仍是本次 Codex 规则。
3. 若模块返回 `504 Outdated Optimize Dep`，按
   [运行时规范](runtime-guardrails.md#9-development-and-browser-test-caches) 检查缓存隔离。
4. iframe 成功后仍未就绪，才继续核对连接器初始化、当前用户的精确钱包选择、
   Wagmi 激活和恢复过程；钱包已就绪后再检查账户模式与资金订阅。
5. 验证持续更新的账户数值与记录、正常钱包菜单，以及缺数据时动作仍被禁用。
   只看到邮箱、行情“已连接”或一次缓存值，都不能证明钱包链路正常。

不通过改写已安装客户端、代理钱包 iframe、关闭安全策略、强行设置 ready 或
自动刷新页面来规避环境限制。SDK 或浏览器将来升级后，应重新验证本案例再更新结论。
