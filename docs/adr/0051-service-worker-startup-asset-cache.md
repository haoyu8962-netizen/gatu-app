# ADR 0051：Service Worker 先存好新壳的启动资源再换壳

- 状态：已接受并实施（2026-11-12）。分支 `claude/fix-sw-asset-cache`，未合入 `dev`、未发布。真机未验收：发布后冷启动是否不再依赖网络，只能在 iPhone 主屏幕应用上对两个连续版本确认。
- 关联：[ADR 0005](0005-spa-static-shell.md)（静态 SPA 壳）；[ADR 0006](0006-startup-preloads-and-edge-caching.md) 第 10 条（热访问由 Service Worker 回答导航）；[ADR 0010](0010-blank-until-ready-startup.md)（空白到就绪的启动）；[ADR 0020](0020-legal-pages-in-app-shell.md)（Service Worker v10）；[运行时守则](../runtime-guardrails.md) §8；[CloudFront 部署](../../deploy/cloudfront/README.md)；[首屏加载调研](../architecture/hyperliquid-first-load-investigation.md)；审查记录 `docs/work-memory/sessions/2026-11-12-global-defect-review.md`（提交 `9395acca`，P1-6 与 P3 字体缓存）。

## 背景

运营方在 iPhone 上把终端添加到主屏幕，隔一段时间再打开，先白屏约 5 秒。按 ADR 0010，运行时、语言目录和字体就绪之前页面是空的，所以白屏多久就是冷启动用了多久。审查找到两处让冷启动依赖网络的问题：

1. **字体缓存从未写入。** `sw.js` v10 的 `cacheFirst` 在 `caches.open()` 的回调里才调用 `response.clone()`，那时响应已交给页面、响应体已被占用，克隆抛错并被吞掉。审查在线上 Chromium 与 WebKit 里看到 `fonts-v10` 为 0 条；本次用 `apps/terminal/tests/browser/sw-release-switch-probe.mjs` 对 v10 的代码（只把缓存名改成 v11）在本机 Chromium 与 WebKit 里复现了同样的结果：字体请求之后字体缓存仍为空。启动闸门等字体，最多 3 秒（`lib/fonts/font-readiness.ts`）。
2. **每次发布后，冷启动要在空白期重新下载几乎整个启动闭包。** v10 只处理导航、字体和币种图标，`/assets/*` 不经它，只靠浏览器的 HTTP 缓存；导航的后台刷新拿到新壳就覆盖缓存，不管新壳引用的资源在不在本机。构建的分块有哈希级联（名为 `vendor-tanstack-router` 的块装着应用入口与共享代码，第三方库的块静态导入它），审查统计任何改动都会让 117 个预加载块里约 111 个改名，约 1.5 MB gzip。于是发布后第一次启动用旧壳（快），第二次启动用新壳，在空白期从网络取回这些块。iOS 是否保留主屏幕应用的 HTTP 缓存也不确定。

官方终端用 Workbox 预缓存整站（约 468 项）规避了第二个问题。

## 目标与约束

- 发布后的冷启动不再在空白期等启动闭包的网络下载：新壳只在它引用的启动资源都已存进本机之后才被使用。
- 字体缓存真正生效。
- 不改变导航的既有行为：旁路清单（`/join`、`/api`、`/client-error-report`、`/mobile-agent-sync*`、`/_serverFn/`、带扩展名的路径）、`?lang=` 的网络优先、壳的可缓存判定（200、未重定向、`text/html`）、图标的 stale-while-revalidate、`skipWaiting` 与 `clients.claim`、退役缓存的清理。
- 写缓存失败（包括 iOS 存储配额不足）不能影响当前请求，也不能阻止设备更新到新版本：先存后换是冷启动优化，不是换壳的前提。后台工作被中途终止时，保持旧壳。
- 缓存不随发布无限增长，失败的候选发布也不能在缓存里越积越多。
- 不改分块策略、启动闸门、`client.ts`、`__root.tsx`、manifest，也不加任何启动期界面内容。

## 决策

1. **缓存版本升到 v11，新增 `assets-v11`。** 退役清理的识别规则加入 `assets-` 前缀，激活时删除 `shell-v10`、`fonts-v10`、`icons-v10` 和其他版本的 `assets-*`。
2. **字体在交出响应之前同步克隆。** `cacheFirst` 先 `clone()`，再把副本写入缓存（`event.waitUntil`），写入失败被吞掉。图标的 stale-while-revalidate 有同类时机问题（`await cache` 之后才克隆），一并改为在回调开头同步克隆。
3. **`/assets/` 走缓存优先。** 范围与 `deploy/cloudfront/deploy.mjs` 的 `objectCacheControl` 判为 immutable 的 `assets/` 一致：同源 GET、路径以 `/assets/` 开头、没有查询串、不是 `.br`/`.gz`/`.zst`，且不带 `Range`。命中（`ignoreVary`，文件名带内容哈希）就直接回答，不发网络请求；未命中就取网络，合格的响应写入 `assets-v11`。合格指：200、未重定向、`Cache-Control` 不含 `no-store`，并且内容类型与扩展名相符——`.js`/`.mjs` 必须是 JavaScript 类型（`text/javascript`、`application/javascript` 等，带不带 `charset` 都行），`.css` 必须是 `text/css`，其余扩展名只要求不是 `text/html`。构建产物的 `/assets/` 里只有 `.js`、`.css` 与 `.woff2`（2026-11-12 的构建：450、2、8 个）；`aws s3 sync` 按扩展名推断类型，`.js` 是 `text/javascript` 或 `application/javascript`，字体可能是 `font/woff2` 也可能是 `binary/octet-stream`，所以字体不加类型限制。线上 CloudFront 实际返回的类型本次没有核对。同一个 URL 同时只有一个网络请求，页面与后台预取共用：第一个响应从不被读取，页面和缓存各拿一个克隆，所以不会在已交出的响应体上克隆。每次下载的结果分三种：已存入；网络侧失败（请求失败、响应不合格、响应体没有读完）；存储侧失败（响应合格，但 `cache.put` 抛错，例如配额不足或 `Vary: *`）。
4. **TradingView 的哈希文件不纳入。** `charting_library/bundles/*` 与带哈希的加载器副本同样是 immutable，但它们体积大、只在 TradingView 升级时改名、由图表 iframe 在工作区显示之后才请求，不在空白期的关键路径上；`chart-asset-cache-policy.test.ts` 也要求 Service Worker 不拦截图表请求。它们继续靠 HTTP 缓存。
5. **换壳之前先存好新壳的启动资源。** 导航（包括 `?lang=` 的网络优先）拿到可缓存的新壳后，在后台：
   - 从壳里读出同源 `/assets/` 引用：`<link rel="modulepreload|preload|stylesheet">` 的 `href`、`<script src>`，以及 `scripts/inject-shell-preloads.mjs` 写入的 `sairn-preload-desktop` 与 `sairn-preload-mobile` 两个 `<meta>` 列表（引导入口按设备读取的启动块）。HTML 注释和内联脚本的正文先剥掉，引号里的 `>` 不会截断标签；`sairn-chart-prefetch` 与图标、manifest 不读。
   - 并发 6 个，把缓存里没有的取回并写入 `assets-v11`；已经在缓存里的不发请求。
   - 每个引用都已取回且合格后，才替换 `shell-v11` 的条目。都存进缓存是正常情况；有的因为存储侧失败没存进去时，照样换壳（退回 v10 的行为，那几个资源下次启动从网络或 HTTP 缓存取）。只有网络侧失败或超过 60 秒总时限才保留旧壳：那代表发布本身不完整或网络不通，保留旧壳是保护；已经存好的资源留着，下一次导航从缺的那几个继续。旧壳仍然可用，因为 `deploy.mjs` 从不删除 S3 上的旧资源。
   - 预取发起的请求带 `AbortController`。任务停止（超时或网络侧失败）时，仍未完成、而且没有页面在共用的下载被中止并移出共享表，下一次导航会重新请求；页面在共用的下载不中止。
   - 替换在一个串行的提交队列里进行，每次提交最多等 10 秒，存储调用挂起时队列照样往下走。编号在写入之前紧挨着检查并占用：多个导航拿到同一份新壳时共用一个任务，每次刷新按开始顺序编号，一份较早开始的壳不会覆盖已经提交的较新的壳；超时后才恢复的提交不再写入。已经发出、但挂起超过 10 秒后才完成的那一次 `put` 无法撤回，这是剩下的窗口。
   - 取回的壳与缓存里的逐字节相同、且两个 CSP 头（`content-security-policy`、`content-security-policy-report-only`）也相同时，任务直接结束：不查资源、不重写壳。正文相同而 CSP 头变了（边缘函数改了策略、没有新构建）时，只重写壳以带上新头，不预取。上次经存储侧失败换壳、资源不全的情况，由页面按需加载时补存。
   - 缓存里没有壳（首次安装、v10 升级之后）时，页面直接用网络壳，资源经第 3 条写入缓存，后台任务照常预取后提交。
6. **容量：出现候选发布时先淘汰，再预取。** 取回的壳与缓存里的壳不同（有缓存壳的前提下）时，预取之前先删掉 `assets-v11` 里既不被缓存壳、也不被这个候选和其他进行中的任务引用的条目：更早版本的资源、懒加载过的块、以及先前失败的候选留下的部分资源。淘汰不再取决于换壳成功，所以存储写满时它照样腾出空间，失败的候选也不会累积。壳没有变化时不淘汰，懒加载过的块留着；首次接管（没有缓存壳）时也不淘汰。正常情况下缓存约为缓存壳与当前候选（或刚换下的上一个壳）的启动闭包，加上自上一个候选出现以来懒加载过的块；后者不超过一次构建的资源总数。这是正常路径上的估计，不是硬上限：多个候选同时在途时它们的资源都受保护，淘汰与预取并发时也可能多留或少留个别条目（少留的由页面按需取回）。没有另设条目数或字节上限：Cache API 不提供访问时间，按插入顺序淘汰会误删当前壳的启动块。
7. **不做整站预缓存。** 只缓存壳实际引用的启动资源和用到过的不可变资源。
8. **CSP 与部署不需要改。** 预取是同源请求，`connect-src 'self'` 已允许；`sw.js` 仍以 `no-store` 上传（`deploy.mjs` 的 `NO_STORE_FILES`），注册时 `updateViaCache: "none"`，新版本在下一次导航时安装并立即接管。

## 备选方案

| 方案 | 取舍 |
| --- | --- |
| 官方的整站预缓存（Workbox，约 468 项） | 首次安装就下载全部路由、对话框和语言目录，大部分用户用不到；首屏调研把它列为「不能复制」，理由是首次安装成本高。本方案只取壳引用的启动闭包，范围更窄。未采用 |
| 只做 `/assets/` 缓存优先，不改换壳时机 | 新壳的资源仍要在第一次用新壳启动时从网络取回，正是白屏的来源。未采用 |
| 换壳后由页面预取下一版资源 | 页面不知道下一版是什么；Service Worker 拿到新壳时已经有完整清单。未采用 |
| 按条目数或字节上限、按最久未用淘汰 | Cache API 没有访问时间，要自己维护元数据；按插入顺序会淘汰当前壳的启动块。按「当前与上一个壳」淘汰与发布节奏一致，界限也清楚。未采用 |
| 把 TradingView 的哈希文件也纳入 | 体积大、不在空白期的关键路径上，且现有契约要求不拦截图表请求。未采用（见决策 4） |
| 修分块的哈希级联 | 能减少每次发布改名的块数，但属于构建策略，不在本次范围。列为后续 |

## 后果与边界

- 代价：每次发布后，已安装用户在后台多下载新壳的启动闭包（约 1.5 MB gzip；缓存存的是解码后的响应体，占用更大）。手机端也会预取 `sairn-preload-desktop` 里只有桌面用的块（数量见当次构建的壳），因为 Service Worker 不知道设备布局。
- 首次安装后的第一次启动仍走网络：第一次访问时 Service Worker 还没接管，资源只进 HTTP 缓存；v10 升级到 v11 时也一样，因为 v10 的缓存被清理、`assets-v11` 是空的，升级后的第一次冷启动要从网络取回启动闭包。
- 后台预取要在 Service Worker 存活期间完成。浏览器（尤其是 iOS）可能在页面离开后很快终止它；那样旧壳保留，下一次导航从缺的资源继续。如果每次都在取完之前被终止，新版本会一直推迟，推迟多少次取决于每次能取回多少，不保证只晚一次。
- 发布后第一次启动仍然是旧版本（与 v10 相同）；新版本在后台取回启动资源之后的下一次启动生效。网络一直不通或发布本身缺文件时，旧版本会一直保留到这种情况消失。存储侧失败不再推迟更新，但那次换壳之后的冷启动有一部分资源仍要走网络。`?lang=` 的链接照旧直接用网络上的当前壳。
- 只读壳里的链接，不解析 JavaScript：入口在运行时动态加载、又不在壳的预加载与两个 `<meta>` 列表里的块，仍在第一次用到时从网络取回并写入缓存。
- 写缓存失败只让缓存不生效：页面照常拿到网络响应，壳照样更新。
- 内容类型检查挡住了「200 但内容是错误文本」的 `.js`/`.css`，但一个类型正确、内容错误的文件仍会被存下并一直命中，因为文件名带哈希、不会再请求。启动失败时清掉资源缓存的自救通道本次不做（见后续）。

## 验证

- 第二轮（2026-11-12，复核与 Codex 对抗审查之后）：修了配额死锁（存不进就不换壳、不换壳就不淘汰）、超时不释放下载、提交队列可被挂起的存储调用堵住、失败候选的资源不回收、错误内容被永久缓存、HTML 注释与引号内 `>` 的解析，以及壳没变时的多余工作。单测增至 4 个文件 99 条，全部通过且 Vitest 退出码为 0（第一轮的「与 deploy 范围一致」测试留下 4 个未处理拒绝，使 Vitest 以退出码 1 结束，第一轮报告只引用了通过数，没有注意到）。第二轮做了 30 个单项变异，全部有测试变红，包括 Codex 指出第一轮抓不到的四个：`ignoreVary` 改为 false、并发 6 改为 1、删掉 `!redirected`、删掉下载结束后的清理。探针新增两个场景，用第一轮的 `sw.js` 运行时两种引擎都失败：失败候选的资源累积；`Vary: *` 资源让壳停在旧版本。
- 第一轮单测（Vitest，在 `node:vm` 里加载真实的 `public/sw.js`，模拟 `fetch` 事件与 Cache Storage）：`apps/terminal/src/lib/tests/sw-asset-cache.test.ts` 覆盖字体与 `/assets/` 下字体的写入与离线命中、资源缓存优先、404 与 HTML 回退不写入、写缓存失败仍回答页面、不拦截的请求（根目录文件、TradingView、其他来源、查询串、预压缩文件、Range、POST）、与 `deploy.mjs` immutable 范围一致、新壳有一个资源取不回时旧壳不被替换、全部存好后才替换、写入失败或提交前资源不在时不替换、60 秒总时限、页面与预取共用请求、同一份新壳只预取一次、较早的壳不覆盖较新的、发布切换时的淘汰与进行中任务的保护、壳不变时不淘汰、`?lang=` 先回答网络壳后缓存、从真实壳结构读出的资源清单、`<meta>` 名称与构建脚本一致。`sw-navigation-cache.test.ts` 与 `chart-asset-cache-policy.test.ts` 改为 v11 名称，其余断言不变。新测试先在未修复的 `sw.js` 上运行，29 条里 18 条失败；只把 v10 代码的缓存名改成 v11 时 17 条失败，其中包括两条字体测试，说明它们抓的是克隆时机而不是缓存名。再做 16 个单项变异（字体克隆放回异步回调、去掉 `/assets/` 路由、预取忽略失败、去掉提交前核对、去掉编号检查、去掉淘汰、壳不变也淘汰、去掉下载去重、去掉任务去重、去掉总时限、预取前就写壳、淘汰不保护进行中的壳、写入 HTML 回退、不读 `<meta>`、不剥内联脚本、退役清理不识别 `assets-`），15 个都有测试变红；没变红的是「预取忽略失败」，因为提交前核对兜住了它，两者一起去掉时 3 条变红。
- 浏览器探针：`apps/terminal/tests/browser/sw-release-switch-probe.mjs` 在 Chromium 与 WebKit（Playwright）里运行真实的 `sw.js`，对一个本地服务轮换三个合成版本：版本 A 的资源进入缓存；部署 B 后导航仍由 A 回答，B 的资源存好后才换壳；随后让 `/assets/` 全部返回 503，新开页面仍启动 B，服务器没有收到资源请求；版本 C 有一个资源取不回时壳保持 B；`/assets/` 之外的字体写入字体缓存。第二轮加了两个版本：D 与 C 一样有资源取不回，核对 C 留下的资源已被删掉；E 的一个资源带 `Vary: *`（真实 Cache API 在每个引擎上都拒绝存它），核对仍会换到 E、新开页面能启动 E。配额耗尽没有模拟：足以挡住资源的配额也挡住壳本身的写入，隔离不出资源路径。2026-11-12 本机两种引擎全部通过；用 v10 的代码（缓存名改为 v11）运行时，两种引擎的字体缓存都是空的。合成版本只有两个文件，不是终端本身，读数不代表真实构建或 iOS 的启动时长。
- 需要运营方做的：在 iPhone 主屏幕应用上，连续发布两个版本后各冷启动一次，确认第二个版本生效那次启动的白屏不再随网络变长；也确认 v11 首次接管后的那一次冷启动只是一次性的网络启动。

## 后续

- 分块的哈希级联（`apps/terminal/vite.config.ts` 的 `manualChunks` 把入口与共享代码放进 `vendor-tanstack-router`）：拆开后每次发布改名的块会少很多，后台预取的量随之下降。
- 如果真机确认 iOS 在页面离开后很快终止 Service Worker、导致预取总是完成不了，再考虑在页面可见时由页面触发一次补齐（例如 `postMessage`），本次不做。
- 自救通道：启动失败（入口模块或启动块加载出错）时清掉 `assets-v11` 并从网络重试一次，处理「类型正确、内容错误」的缓存条目。它与「入口脚本加载失败的兜底页」那项后续工作相关，应一起设计，本次不做。
