# ADR 0037：精确小数串经 `formatDecimalString` 按数字格式设置显示

- 状态：已接受并实施（2026-10-02，分支 `claude/angry-northcutt-d85ed7`，叠在未推送的 `claude/wonderful-goldberg-e47b19`（ADR 0036）上）；未推送、未合入、未发布。2026-10-03 追记：已随集成分支 `claude/integrate-locale-number-format` 并入 [PR #71](https://github.com/zora4523-bot/gatu-app/pull/71)，PR 尚未合入 `dev`，也未发布。
- 关联：[数字格式设置](../number-format-setting.md) 规则 10；[ADR 0036](0036-render-time-number-formatters.md)「后果与边界」登记的手写格式后续；[任务记录](../work-memory/sessions/2026-10-02-exact-decimal-number-format.md)（分类表、先失败的用例与验证）。

## 背景与约束

- 数字格式设置（`1,234.56`、`1.234,56`、`1 234,56`）要求每个数字都跟随它（规则 1）。`lib/format.ts` 的格式化函数先把值转成 JS 数字，再交给 `Intl` 按设置替换分隔符。
- 有一批显示没有经过 `lib/format.ts`，固定输出 `,` 分组和 `.` 小数点，或者干脆没有分组：
  - ADR 0036 登记了七类：质押、金库、跨链到账、手机行情条涨跌、手机下单页涨跌幅、下单费率、TP/SL 风险收益比；
  - 本次把全仓 119 处 `toFixed` 与 `lib/format.ts` 的 `bpsToPercentage` 逐处追踪到使用处，共 120 行。其中 33 处拼出了绕过设置的展示文本，23 处在默认生产构建中可见。其余 10 处：1 处在只有嵌入式挂载、被 CSS 隐藏的块里，1 处只在缺少市场元数据的回退路径上，8 处在默认关闭的 LiFi 跨链开关后面；
  - 另外 37 处只经 `lib/format.ts` 显示，39 处从不显示，8 处是仅开发环境的排行榜夹具，3 处没有生产调用方。
  - 追踪时还记下了几处不经 `toFixed` 的同类显示（不是穷举）：
    - 下单面板与手机摘要的滑点 `2.5%`、规模单的规模偏斜与范围 `0.01–100`；
    - 平仓、全部平仓通知里子订单的原始数量；
    - 金库确认页原样显示的输入金额；
    - 充值表单直接显示 viem `formatUnits` 的余额与手续费；
    - 订单簿整数分组标签 `1000` 没有分组；
    - LiFi 的 `toPrecision` 与 `<0.0001` 一类字面量。
- 约束：
  - 这些多是精确十进制：质押数量 8 位小数、金库金额超过双精度（单测钉住 `$9,007,199,254,740,993.01`）、按 `Big.roundDown` 截断的可用余额与比例，位数和舍入方向不能变；
  - 渲染期要按 ADR 0036 从 `useNumberFormat()` 取函数，切换设置时当场更新，不重挂载、不丢输入；
  - 输入框的值、协议值与比较仍用 `.` 协议串（规则 6）；
  - 规则要能用源码级测试检查。

## 决策

用户在三个方案里选了第一个，范围选「全部已核实的可见显示」，契约选「全仓登记制」。

1. **`formatDecimalString` 只换分隔符。** `lib/format.ts` 新增 `formatDecimalString(value, { trimTrailingZeros? })`，并放进 `NumberFormatters`，所以每次设置变化都换新的函数身份。
   - 输入是调用方已经按自己的规则取整或截断好的纯小数串（`[+-]?数字[.数字]`），例如 `Big(value).toFixed(4, Big.roundDown)` 的结果、协议价格与数量、viem `formatUnits` 的结果。
   - 函数按设置插入分组符（三位一组，与 `en-US` 的 `Intl` 一致）、替换小数点，可选去掉末尾的 0。数字一位不改，所以超过双精度的值与调用方的舍入方向都保留。整数部分多余的前导 0 会去掉：`0005` 分组后会读成 `0,005`（德式格式下 `0.005`），而值没有变。
   - 不是纯小数串（指数写法、`<0.0001`、空串）时返回占位符，不猜分隔符。
2. **调用方保留取整规则，显示处才格式化。**
   - 质押、金库、跨链、费率、风险收益比、手机涨跌的展示 helper 增加 `numberFormat: NumberFormatters` 参数（ADR 0036 决策 3），把 `toFixed` 的结果直接交给 `formatDecimalString`，删除手写的分组正则。
   - 协议串在显示处格式化，包括：下单通知与子订单的数量、划转与发送的「可用」余额、下单面板持仓数量、提现最低额、订单簿分组标签、TWAP 触发价提示、两个 Mid 按钮的读屏名、资金恢复通知、质押操作参考里的金额、平仓滑杆的读屏文字、充值表单的余额与手续费。
   - 用户输入的金额（金库确认页、充值进行中的状态行）先经 `lib/trade/numbers.ts` 的 `toPlainDecimal` 用 Big.js 规范成提交路径使用的写法（`0005` → `5`、`5.` → `5`），再交给 `formatDecimalString`。
   - 本来就是 JS 数字的（滑点与设置弹窗里的滑点范围、规模偏斜与订单数、跨链耗时）用 `formatNumber`。规模偏斜按 `SCALE_SKEW_MAX_DECIMALS` 保留 4 位。
   - 用 Lingui 占位名的消息保持原变量名（如 `minimum`、`triggerPrice`、`balance`、`cctpFee`、`requestedPercent`），只换成格式化后的值，所以消息 ID 与六种语言的译文不变。原始值仍传给需要计算的子组件（`UnitDepositInfo`、`AmountInput` 的 Max）。
3. **技术整数保持原样。** 原子数量（wei）、原子小数位、金库操作参考串和身份纪元在恢复详情和参考行里照原样显示，便于逐位核对与复制。
4. **契约 `decimal-display-contract`。** 用 TypeScript AST 扫描 `apps/terminal/src` 的非测试源码：
   - 每个 `.toFixed(`、`.toPrecision(` 要么写在 `formatDecimalString(...)` 第一个参数的表达式里，要么所在文件已按用途登记了精确次数；
   - 新文件、次数变化或过期的登记都失败；
   - `lib/format.ts` 以外不得出现手写千分位正则（`\d{3})+` 或 `[0-9]{3})+`）；
   - 附检查器自身的正反样例。登记了 37 个文件、102 处调用，每处写明用途（协议值、输入框、计算、开发夹具、交给 lib/format 前的取整，或显示处如何格式化）。

## 备选方案与代价

- **lib/format 内置精确格式化。** 例如 `formatExactDecimal(value, { decimals, rounding, trimZeros, signDisplay })`。取整也收进 `lib/format`，展示代码不再写 `toFixed`，契约更简单。代价是每处现有规则都要重新表达成选项，改动更大，容易引入细微的行为变化。未采用。
- **转成 JS 数字，走现有的 `formatNumber`/`formatPercent`。** 调用最简单，但有三个问题，未采用：
  - 精度：`9007199254740993.01` 会显示成 `$9,007,199,254,740,994.00`（2026-10-02 用 Node 实测）；
  - 舍入：`Intl` 按最短十进制写法舍入，`toFixed` 按二进制值舍入，`1.005` 分别得到 `1.01` 和 `1.00`；
  - 截断：要依赖 `roundingMode: "trunc"`，MDN 兼容数据显示它需要 Chrome 106、Firefox 116、Safari 15.4，而 Vite 7.3 的默认构建目标含 Firefox 104。旧版会忽略该选项，「可用余额」可能被向上取整。
- **把字符串直接交给 `Intl.NumberFormat`。** 字符串精确小数与 `roundingMode` 同属 NumberFormat v3，浏览器要求同上；更旧的引擎会先把字符串转成数字，静默丢精度。未采用。
- **契约只管组件文件，或不加契约。** 本次的问题大多在 `.ts` 展示 helper 里，只查 `.tsx` 一处也拦不住；不加契约则只能靠评审。未采用。

## 后果与边界

- 英文格式下，原来缺千分位的显示补上了分组，例如：
  - 手机行情条涨跌额 `+2345` → `+2,345`；
  - 跨链到账 `1234.57 USDC` → `1,234.57 USDC`；
  - 可用余额 `4964.51 USDC` → `4,964.51 USDC`；
  - 下单通知 `Bought 1234.5 HYPE` → `Bought 1,234.5 HYPE`；
  - 提现最低额与订单簿 `1000` 标签同样加上分组。
- 除分隔符外的行为变化：
  - 跨链「发送数量」取 5 位有效数字后达到 10 万的（从 99,999.5 起）原来显示成指数写法（`1.2346e+5`），现在保留全部整数位、按剩余小数位取整（`123,457`）；更小的数量与原来的 5 位有效数字逐位相同，包括进位到下一位的边界（`9.99996` 仍为 `10.000`）；
  - 质押比例极小（如 `1e-10`）时原来显示 `—%`，现在显示 `0%`；
  - 金库确认页与充值进行中的输入金额改为提交时的规范写法（`0005` 显示为 `5`）；
  - 滑点最多显示 3 位小数，规模偏斜最多 4 位，此前直接输出 JS 数字。
- 契约只看名字与语法位置。已登记 helper（`floorToString`、`formatPriceForOrderWithRounding`、下单成交摘要、订单簿分组标签、提现金额）返回的协议串在别处显示时，契约跟不到。由登记的用途写明显示处如何格式化，新显示须遵守规则 10。
- 资金类提示在弹出时格式化，已显示的提示不随设置变化，这一约定不变（质押成功通知现在用弹出时的设置）。资金恢复通知由宿主组件持续渲染，会随设置当场更新。
- 没有改动：仅开发环境的排行榜夹具；没有生产调用方的 `bpsToPercentage` 等三个函数；组合收益图手写的日期刻度（属于日期规则）。
- 构建体积：按固定输入成对构建，客户端总量 +1,216 字节、桌面运行时启动 +170、手机 +83；预算基线按惯例相应提高。基线提交本身超出总量上限，见任务记录「验证与限制」。（2026-10-03 追记：集成后在干净 worktree 里用同样的固定元数据重测，本 ADR 的改动为总量 +1,392、桌面运行时 +91、手机 +79。脚本里的上调注释已按此改写。同一基线提交在那里测得在预算内，与上面的说法相差 2,915 字节，原因未查。见[集成记录](../work-memory/sessions/2026-10-02-integrate-locale-number-format.md)「第二次集成」。）
