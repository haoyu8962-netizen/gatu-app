# ADR 0021：Earn 页接入借贷储备池

- 状态：已接受并实施，2026-09-27；尚未发布。真实账户验证：存入与 Max 全部取出已由用户在自己的主网账户完成并核对（见任务记录）；借入与偿还没有做真实测试，成功通知的实际显示没有观察到。 2026-10-08 补记：之后随 p24 发布（main `3ced842e`，2026-10-02）。
- 编号：原为 0020。2026-09-27 合并 `dev` 前改为 0021，因为 `dev` 先合入的“文档与法律页并入应用外壳”已使用 0020；PR 讨论、审查记录与此前提交里的 “ADR 0020 Dn” 都指本文。
- 归属 Reference：[Earn](../earn.md)。关联：[确认面契约](../confirmation-surfaces.md)、[资金类弹层的结果反馈](../funds-dialog-outcome-plan.md)、[ADR 0013](0013-desktop-navigation-collapse.md)、[ADR 0002](0002-exact-owner-trading-signers.md)。

## 背景与目标

导航里的 Earn 一直是禁用的 “Soon” 占位。官方终端的 Earn 页是 HyperCore 借贷储备池的前端：存入计息资产赚息、存入抵押品借入、偿还与取出。产品负责人要求按官方开发文档、SDK 文档和官方终端的实际做法实现，文档说不清的地方以官方终端为准。

目标是第一版覆盖标准账户与统一账户的四种操作，并保持现有签名、确认面、资金动作、被动数据展示和导航契约。

## 约束

- 签名身份按 ADR 0002：只用与所选 Hyperliquid 用户地址完全一致的签名方；邮箱账户不生成、不批准本地 Agent。
- 确认面契约：执行不超过用户点击时看到的值；确认按钮名是静态动词；资金类弹层保持打开到请求结束，结果走通知。
- 被动数据不显示加载、失效或错误文字；缺失、失败或不匹配的快照不能当作空账户。
- 金额运算用 Big.js，协议值保持小数字符串。
- 锁定的 SDK 为 0.33.3，不为本功能升级 SDK。

## 决策

1. **D1 交易签名方。** `borrowLend` 是 L1 action，走 `useExchange` 的交易客户端：邮箱账户用自己的嵌入式钱包，外部钱包用已验证的 Agent。官方前端同样传入 Agent 钱包签名。确认按钮使用 `TradingActionButton`（不要求 builder fee），签名方未就绪时先启用交易。
2. **D2 发送展示的精确数量；全部取出与全部偿还例外（2026-09-27 修订）。** 官方点击 Max 后发送 `amount: null`（链上按全额执行）。原决策是一律发送弹窗展示的精确小数字符串，并在发送前用刷新后的储备池与仓位重算 Max，要求发送量 ≤ 展示的 Max 且 ≤ 最新 Max，否则失败关闭。
   修订原因：真实账户测试中，点 Max 全部取出被交易所以 `Borrow/Lend error: Minimum amount supplied is $1` 拒绝。存款价值随利息持续增长，精确数量到执行时总会留下不足 $1 的零头，而交易所要求存入余额为 0 或至少 $1，所以按原决策全部取出不可能成功。
   现行规则：取出或偿还时，用户点 Max 的那一刻若没有抵押要求、池流动性或现货余额限制全额（`getEarnFullPosition`），就记下一个全额意图（账户身份、操作、资产、本金 `basis`），请求改为全额（`amount: null`）；点 Max 时受限的，始终按显示的精确数量提交，之后即使限制解除也不会自动改成全额。弹窗写明“在执行时取出全部存款（或偿还全部借款），含已产生的利息”，承诺的对象是执行时的整个仓位，不是一个数字。本金或身份变化、全额不再可行时，全额意图作废，提示重新点 Max；判断时从未按操作过滤的完整快照里找冻结的资产，偿还时借款已经还清（偿还列表里不再有这个资产）也算作废（第五轮审查后补）。用户一旦修改数量、切换资产或账户变化，就回到空白或精确数量。成功通知写“全部 USDC 存入”，不写具体数字，因为交易所响应里没有实际执行量。存入与借入仍然只发送精确数量。
   残余窗口（第三、四轮审查指出，2026-09-27 修订）：交易所请求里没有本金条件，客户端无法把执行时的本金原子地绑定到请求上。现在的顺序是：拿到跨标签页资金锁 → 强制刷新法律校验 → 进入签名会话锁 → 锁内重新请求储备池、仓位、账户模式与地区，按最新数据校验本金与全额可行性（D12）→ SDK 边界的同步检查（锁内快照与本页最新缓存都要满足）→ 签名并发送。锁内复核是新请求，所以本浏览器其他标签页先完成的资金动作只要已反映在 info 接口里就会被看到（交易所返回后 info 接口是否立即一致没有验证）。剩下的窗口是锁内复核之后的签名与网络传输（时长没有测量）：这段时间里如果这个仓位被别处改变——同一账户在别的客户端（官方终端、另一台设备）的操作、代表该账户签名的 Agent/API 钱包，或清算——交易所会按执行时的全额处理；这些事件具体怎样改变 `basis` 没有取得协议样本。取出时多出的部分回到用户自己的现货；偿还时多扣的现货用来偿还同一账户新增的借款，账户净值不变，但现货与可用保证金会减少。这是确认面契约“执行不超过展示值”的一个有意、记录在案的例外：精确数量无法清空持续计息的仓位（交易所的 $1 下限），官方终端对 Max 的处理与此相同。全额偿还要求现货至少覆盖借款加一小时利息，给签名与传输期间的计息留出余量。
   同时按交易所规则做前端校验：手动输入的取出会让余额低于 $1、或存入后余额低于 $1 时，禁止提交并提示改用 Max 或至少保留 $1。这条规则来自交易所报错，官方文档没有写；借入与偿还是否有同类下限没有证据，没有加校验。交易所返回这条报错时显示翻译后的可操作说明。
3. **D3 资金类弹层生命周期。** 与划转、发送一致：请求期间弹窗保持打开且不可关闭，按钮名不变，结束后关闭并通过全局通知报告成功、失败或未知。传输结果不明报告为常驻警告，不当作失败。第一版不建持久化的资金动作标记。通知内容由 `EarnOutcomeToastContent` 渲染：记下发起时的网络与账户，身份变化时撤下自己，文字随当前语言重新翻译（2026-09-27 审查后补）。
4. **D4 纳入跨标签页资金锁。** `borrowLend` 加入 hl-react 的 `FUNDS_ACTION_METHODS`，同一账户的资金动作串行执行，锁内强制刷新法律条款校验。
5. **D5 门控。** 页面与弹窗复用 `useFundsActionAvailability`：地区受限或无法判定、手机 Agent-only 会话、没有钱包访问、账户模式未知或不支持、账户数据未就绪时禁用全部操作。在此之上按官方规则判定各按钮（没有存入不能取出、没有抵押品不能借入、没有借款不能偿还）。
6. **D6 组合保证金账户。** 与官方一致，手动存入、取出、借入禁用并显示官方说明；已赚/应付利息列隐藏；清算价改用维持后可用额计算。偿还也禁用：官方在组合保证金下的偿还是卖出抵押品的现货兑换流程，本版未实现。
7. **D7 利息与历史。** 利息页签用 `userBorrowLendInterest` info 接口轮询最近 30 天，按时间游标分页拉完，窗口起点在每次请求时计算（SDK 0.33.3 没有这个订阅，官方用的是 WebSocket 推送）。操作历史复用共享账本，账本在截断前单独保留 `borrowLend` 记录（`earnRows`）。
8. **D8 导航。** Earn 改为常驻一级入口（`placement: "primary"`，链接 `/earn`），移动抽屉同步改为链接。1101–1181px 未连接钱包时一级入口因此多一个；实测法语余量不足（见后果），窄屏收纳阈值 `DESKTOP_NAV_NARROW_MAX_PX` 从 1100 调到 1150。
9. **D9 SDK 边界再核验。** 同步执行守卫入队时只核对身份、交易生命周期和参数；到 SDK 边界时要求锁内复核（D12）已完成且不超过 20 秒、账户快照仍就绪、不是组合保证金，并用锁内拿到的快照与本页最新缓存分别重算 Max、校验本金，发送量都必须满足（2026-09-27 第二轮审查后加；第四轮审查后改为同时检查锁内快照，最初的版本只读本页缓存，缓存可能早于另一个标签页刚完成的操作）。
10. **D10 快照完整性与仓位变化提示。** 储备池或仓位出现重复资产、有非零仓位却缺少对应储备池时整张快照不可用；零价格时相关 Max 不可用。弹窗打开后仓位变化时就地提示，不阻止提交（确认面契约第 4 条）。
11. **D11 比官方更保守的 Max 与门控（第二轮审查后补）。** 借入与取出不超过储备池流动性 `balance`；存入与偿还按 min(总额 − 冻结, 维持保证金后可用额) 计算可动用余额；有敞口的资产价格为 0 时整张快照不可用；储备池刷新失败时即使有缓存也禁止提交。官方前端这几处都更宽松，这里宁可少放行。
12. **D12 锁内复核（第四轮审查后补）。** 第四轮审查用资金锁时序证明：锁外核验之后排队，拿到锁时用的仍是本标签页缓存，另一个标签页刚完成的存入不会被看到。`useExchange` 原先只允许用户签名方法使用异步前置守卫（交易签名方法传入会报错）。新增白名单 `TRADING_PRE_EXECUTION_GUARD_METHODS`，目前只有 `borrowLend`，且必须属于资金锁方法：守卫在资金锁内、强制刷新法律校验之后、签名会话锁内运行，抛出的错误原样返回调用方，整体超时 10 秒即失败。Earn 在守卫里并行复核账户模式、地区、储备池与仓位，原先锁外的预核验去掉。储备池与仓位直接请求 info 接口并传入守卫的中止信号，请求前后取消页面上进行中的同名查询，结果写回缓存（第五轮审查后改：原先用页面查询的 `refetch`，按 React Query 5.90.16 源码，它被连续取消时可能返回旧缓存且不带错误）。代价：从等资金锁开始到签名发出，同一交易客户端上排队的其他请求（包括下单，以及撤单、只减仓等优先请求）都要等待。等资金锁最长 10 秒，守卫本身最长 10 秒；法律校验（含重试）、等会话锁与签名发送没有统一的总时限。本 PR 之前已有的交易签名资金动作（`vaultTransfer`、`claimRewards`、`setReferrer` 等）同样在锁内排队并做联网的法律校验，Earn 新增的是守卫这一段网络请求。Agent-only 会话的执行租约带有 active owner，`startAgentRegistrationExecution` 拒绝在这种租约上运行前置守卫；Earn 在 Agent-only 会话里本来就全部禁用（D5），这条路径只会失败关闭。未采用：对所有交易签名的资金动作放开（会改变 `agentSetAbstraction` 等动作的语义）；Earn 自己再拿一次资金锁（Web Locks 不可重入，会与 `useExchange` 内部的同名锁互相等待）。

## 备选方案与代价

| 方案 | 取舍 |
| --- | --- |
| 照官方在 Max 时发送 `null` | 最初未采用，理由是执行量可能超过展示值。2026-09-27 修订为只在取出、偿还且可全额时采用（见 D2）：交易所的 $1 下限使得精确数量无法全部取出；锁内复核之后仍有签名与传输的窗口，窗口内多出的部分回到用户自己的现货或用于偿还同一账户的新增借款（见 D2 残余窗口） |
| 复用金库/质押的分阶段弹层与持久化标记 | 可以在结果未知时提供“再次核验”，但标记机制的对账数据源、状态基线都要为借贷扩展，改动面大。第一版未采用，结果未知只给常驻警告 |
| 升级 SDK 以获得 `userBorrowLendInterest` 订阅，或给 SDK 打补丁 | 影响所有使用 SDK 的路径，超出本任务范围。未采用 |
| 在组合保证金下实现官方的“卖出抵押品偿还” | 需要现货市价单、缓冲倍数与滑点处理，属于另一个交易流程。推迟 |
| Earn 设为 `lower` 入口，与金库等一起收纳 | 不改断点，但与官方（Earn 常驻一级）不一致，已连接时在紧凑宽度会进入 More。未采用 |
| 保持 1100 阈值 | 法语在 1101px 只剩 6px。未采用 |
| 扩展 `useExchange`，让交易签名方法也支持锁内的异步前置守卫，在锁内重新请求储备池与仓位 | 第三轮时未采用，改用同步边界核验。第四轮审查证明同一浏览器的另一个标签页也能绕过锁外核验后采用，范围限定为白名单里的 `borrowLend`（D12） |

- 1101–1150px 的未连接用户，金库、质押、推荐、排行榜改为在 More 中（原来 1101–1181px 都显示在一级）。
- 导航余量实测（2026-09-27，本地开发服务器，未连接钱包，`/earn`，导航最后一项与右侧控件之间的距离）：1101px 下若不收纳为 en 124、zh 237、hi 243、es 50、fr 6、ar 146px；调整后 1151px（不收纳）fr 56、es 100px，1001px（收纳）fr 226px。已连接钱包的状态未实测。
- 真实账户：存入与 Max 全部取出已由用户在自己的主网账户完成，页面、账本与利息记录一致；借入与偿还未做真实测试；成功通知的实际显示未观察到。
