# ADR 0046：订单簿与下单数量共用一个单位，盘口数字完整显示

- 状态：已接受并实施（2026-11-01，运营方「需要决定的八项 请根据官方的实践来修复，确保符合规范」）；分支 `claude/audit-group2`，未合入 `dev`、未发布。
- 关联：[订单簿布局](../orderbook-layout.md)、[最近成交](../recent-trades.md)、[下单面板双端一致](../order-entry-surface-parity.md)；审查项 M2、M9、C5（[第二组记录](../work-memory/sessions/2026-11-01-audit-group2.md)）。

## 背景

- **M9 单位两套来源。** 桌面订单簿与手机紧凑簿跟随下单数量单位 `sizeMode`；手机分栏簿与设置里的「Order book in quote asset」开关读全局设置 `showOrderbookInQuote`；桌面订单簿里没有单位控件；最近成交跟随订单簿单位，可显示计价成交额。
- **官方只有一个状态。** 2026-10-31 官方生产前端包：存储键 `hyperliquid.raw_is_ntl_for_sz_inputs`。订单簿控制行右侧的单位下拉（选项依次为计价币、基础币）用的就是下单表单的 `isNtl` / `setIsNtl`；切换时按限价（没有限价时按标记价）换算已填数量，USD 向下取整到 2 位、基础币到 `szDecimals`。设置页没有单位开关。最近成交表头恒为 `Size (基础币)`，数量按 `szDecimals` 显示。
- **M2 分组值被截断。** 桌面价格列只占 1:2:2 的五分之一，分组下拉挤在价格列头里：1920 宽 kPEPE 的 `0.000001` 显示成 `0.…`；容器不超过 319px 时「Price」列头还被隐藏。官方在列头上方单独一行放分组（左）与单位（右），列头只有文字。
- **C5 数字被缩写。** 我方不小于 10,000 的数量与累计显示为 `10M`、`205K`，单元格还会 `truncate`；官方用 `toLocaleString` 完整显示，计价金额取 0 位小数（数量为 `Pn(px*sz, 0)`，累计为 `Pn(cumNtl, 0)`），窄列允许溢出。

## 约束

- 数量、单位与只减仓留在共享草稿里，跨响应式重挂载保留（`AGENTS.md` 下单契约）。
- 订单簿的行几何、订阅、价格键、选价保护与反馈动效不变（订单簿契约）。
- 价格、数量与累计量必须完整可读，不以缩写或截断换取空间（[订单簿布局](../orderbook-layout.md)目标）。
- 手机下单页左侧的紧凑簿在 320px 宽的手机上只有约 124px 宽；官方没有这种紧凑簿，无可照搬的做法。

## 决策

1. **单位只有一个来源：下单草稿的 `sizeMode`。** 删除全局设置 `showOrderbookInQuote` 与设置弹窗里的开关。旧的存储值不迁移，也不再被任何代码读取：校验存储只校验、不改写读到的对象，所以它会留在内存里的设置对象上，直到下一次保存设置时被持久化白名单（`partialize`）去掉。
2. **订单簿里选单位等于改下单数量的单位。** 桌面控制行与手机分栏簿芯片行的单位下拉，选项依次为计价币、基础币（与官方顺序相同），读屏名称为 `Size unit`。选择后写一次请求 `requestSizeMode(市场, 单位)`；桌面 `TradePanel` 与手机 `MobileTradeView` 用 `useBookSizeModeRequest` 读出即清除，别的市场的请求丢弃，单位相同不处理，否则调用表单自己的 `toggleSizeDenomination` 换算已填数量。换算、只减仓数量来源与草稿行为和表单单位切换完全相同。与官方的差异：表单既有换算优先用标记价（`getConversionPrice`），官方有限价时用限价；这是表单原有行为，本次不改。
3. **最近成交恒用基础币。** 表头为 `Size (基础币)`，数量按 `szDecimals`；删除计价成交额函数 `getTradeQuoteSize`。
4. **桌面订单簿加一行控制行。** 列头上方 24px：价格分组下拉靠左，单位下拉靠右；列头只有文字 `Price / Size (单位) / Total (单位)`。删除「容器不超过 319px 时隐藏价格列头」的规则。默认 670px 面板每侧仍是 11 档。
5. **数量与累计完整显示，不缩写、不截断。** 基础币按 `szDecimals`。计价币与官方一样取整到 0 位；绝对值小于 1 时保留可见小数（`getOrderbookQuoteDecimals`），避免非空档位显示成 0，这一点比官方多。数值单元格靠右，放不下时向左溢出到相邻空白；价格不截断。悬停提示里的计价累计用同一规则。
6. **手机紧凑簿例外。** 每行按实测梯子宽度和 IBM Plex Sans 12px 等宽数字的保守字宽估算（`getCompactOrderbookSizeText`）。完整价格与数量放得下就完整显示；放不下时依次尝试更少的小数位（不把非零数量取整成 0），再尝试从 10,000 起的两位、一位、零位缩写，取第一个放得下的写法；都放不下时取最窄的那个。价格始终完整，读屏名称始终是完整数量。

## 备选方案

| 方案 | 取舍 |
| --- | --- |
| 保留设置开关，订单簿单位独立 | 与官方不同，两个状态仍可能不一致（M9 原问题） |
| 订单簿切单位只改显示，不换算下单数量 | 下单框里的数字悄悄换了单位，数量含义错乱 |
| 在订单簿组件里另写一份换算 | 与表单换算及只减仓数量来源分叉；本方案经请求复用表单实现 |
| 紧凑簿列宽随内容（`1fr auto`，最小 154px） | 320px 下压缩已经很紧的下单列 |
| 紧凑簿也允许溢出 | 320px 实测价格与数量重叠，不可读 |
| 计价币保持 2 位小数 | 与官方不同，窄列更容易放不下 |

## 后果与边界

- 在订单簿里切单位会同时改变下单框的单位并换算已填数量，与官方一致；最近成交不再显示计价金额。
- 手机设置少了一个开关；之前打开过它的用户，手机分栏簿改按下单单位显示。
- 大于 1 的计价金额不显示小数，与官方相同。
- 紧凑簿的字宽是估算值，按实测上取整；换用别的字体或字号时要重新测量。

## 验证

- 新测试先在改动前的提交 `52f9dc18` 上运行，全部失败；在本分支通过。覆盖：控制行与纯文字列头、单位下拉写请求（桌面与分栏簿）、完整数量与累计（桌面、分栏簿）、计价取整、最近成交恒为基础币、设置开关已删除、真实 store 下的单位请求（只生效一次、丢弃别的市场、单位相同不处理）、两端表单的接线、紧凑簿的放不下才缩写。
- 变异 24 个（缩写、截断、计价位数、分组回到列头、单位请求方向、请求的领取与身份核对、市场与单位判断、两端接线、最近成交单位、分栏簿累计、紧凑簿的宽度判断、行内边距、字宽、减少小数位与不取整成 0），全部被抓到。
- Codex 只读对抗审查（订单簿一路，`52f9dc18..7bf9b0b5`）8.0 分：紧凑簿对 10,000 以下、小数位多的数量（如 BTC 的 `123.45678`）没有兜底，仍会与价格重叠；请求在表单挂载前已存在时，StrictMode 下会被执行两次；本 ADR 把旧设置写成「由 schema 丢弃」。三项都已修复：紧凑簿改为上面第 6 条的逐级写法，请求改为按对象身份领取（`takeSizeModeRequest`），第 1 条改为如实描述。
- 浏览器：订单簿四个 Playwright 套件 59 项通过。本地开发服务器、无头 Chromium、未连接钱包，在 320、390、1100、1440 宽测 kPEPE 与 BTC 的基础币与计价币：价格、数量与累计的文字互不重叠，也不超出梯子。测量脚本没有入库，不是真机验证。
