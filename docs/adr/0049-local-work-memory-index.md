# ADR 0049：工作记忆索引只在本地生成，不入库

- 状态：已接受并实施（2026-11-05）。决定来自运营方的要求：「在这里完成此任务：消除 INDEX.md 在并行 PR 间的冲突」。分支 `claude/local-work-memory-index`，未合入 `dev`。
- 关联：
  - [工作记录与检索约定](../work-memory/README.md)、[Agent 工作手册](../agent-handbook.md)、`scripts/work-memory.mjs`；
  - [ADR 0016](0016-dev-first-pull-requests-and-ci-tiers.md) D8：晋升覆盖判定，以及「直接推送 `dev` 会让下一次晋升全跑」。

## 背景

- `docs/work-memory/INDEX.md` 由 `pnpm memory:index` 从任务记录的元数据生成，一直纳入版本控制。
  - `memory:check` 要求它与生成结果逐字相同；
  - `AGENTS.md` 要求改动记录后运行 `memory:index`。
  - 所以几乎每个 PR 都重建并提交它。
- 这个文件有 759 行、约 386 KB（2026-11-05）：
  - 按议题列出每条记录的完整摘要，一条记录属于几个议题就出现几次；
  - 后面还有一张按日期排列的表；
  - 新记录插在各议题的最前面，改摘要也改在相邻的行上。
- 后果：一个 PR 合入 `dev` 后，其它也改了这个文件的开着的 PR 经常冲突。新记录都插在各议题的最前面，改动落在同一处或相邻的行上。
  - 现行的处理方式是：合并 `dev`、重建、再推送。
  - 代码 PR 每推送一次就全跑 CI，一轮约 64 计费分钟，私有仓库每月额度 3,000 分钟。
  - 开着 Auto-fix 时，每次冲突都会自动触发这样一轮。
- 实例：
  - 2026-11-05，#153 在 #151、#154 先后合入后各冲突一次；
  - 此前 #134 两次、#149 一次，见各自的任务记录；
  - 同一时刻 #152、#153 与晋升 PR #155 都改了这个文件。
- 没有任何 CI 工作流运行 `memory:*`，索引是否最新只靠提交前的本地检查。
- `memory:check` 用 `git cat-file -e` 逐个核对记录引用的提交。2026-11-05，本 ADR 之前的记录共引用 890 个不同的提交，一次检查约 18 秒。

## 约束

- agent 开工时要能检索全部记录：`AGENTS.md`「Work memory」，以及手册「开始一个任务」。
- 不直接推送 `dev`，也不为此改 GitHub 设置。
- 任务记录的格式不变，不改写历史记录。
- `memory:check` 继续检查以下各项：
  - 元数据；
  - 议题与来源路径；
  - 提交引用；
  - 替代关系。

## 决策

1. `docs/work-memory/INDEX.md` 不再纳入版本控制：从 Git 中删除，并写进 `.gitignore`。它成为本地视图，仍由 `pnpm memory:index` 生成，内容与格式不变。
2. 任务开始时先运行 `pnpm memory:index`，再查本地索引，或者用 `rg -n '关键词' docs/work-memory`。PR 只提交自己的任务记录。
3. `memory:check` 不再比较索引文件，改为做三件事：
   - 校验全部记录；
   - 确认索引能正常生成；
   - 发现 INDEX.md 仍被 Git 跟踪时失败，防止它重新入库。
4. 提交引用改为用一次 `git cat-file --batch-check` 批量核对。
   - 判定与逐个核对相同：解析不到、或不能剥离为提交的名字都失败，包括缺失的对象、树、文件内容和有歧义的短提交号；指向提交的附注标签按其提交通过；
   - 失败信息写出是哪条记录引用了它；
   - 输出缓冲随名字数量放大，引用再多也不会被默认的 1 MiB 缓冲截断；
   - 一次检查从约 18 秒降到 1 秒左右，开工时生成索引不再费时。

## 备选方案

- **合并后由工作流重建索引并提交到 `dev`**：未采用。原因：
  - 要给 Actions 写权限，这是改 GitHub 设置；
  - 等于直接推送 `dev`，会让下一次晋升全跑（ADR 0016 D8）；
  - 还会和人工合并争抢。
- **用 `.gitattributes` 的合并策略，例如 `merge=union`**：未采用。原因：
  - 自定义合并驱动没法配置到 GitHub 服务器上；
  - GitHub 也没有文档说明，会在 PR 的冲突判定或合并里使用 `union`；
  - 即便用上了，`union` 会同时保留新旧两行，得到的索引是错的。
- **改格式来减少冲突**，例如条目之间加空行、去掉摘要、按议题拆成多个文件：未采用。这些办法能减少改摘要引起的冲突，但同一天、同一议题的两条新记录仍会插在同一位置，照样冲突。
- **只在每周整理时生成并提交索引**：未采用。功能 PR 不碰索引就不会冲突，但库里的索引最多旧一周；agent 要看最新的视图，得在本地重建一个被跟踪的文件，很容易连同 PR 一起提交回去。
- **用 lefthook 的 post-checkout / post-merge 钩子自动重建**：未采用。钩子会在每次切换分支、每次新建工作树时运行，旧分支上有不合格的记录时，每次都打印报错。开工时手动运行一次已经够用。

## 后果与边界

- GitHub 网页上不再有索引。可以在网页上浏览 `sessions/`，文件名以日期开头；议题和归属文档见 `topics.json`。
- 已有的分支或开着的 PR，如果改过 INDEX.md，合入本变更后的 `dev` 时会出现一次「修改/删除」冲突。处理方法是保留删除：
  1. 运行 `git rm docs/work-memory/INDEX.md`；
  2. 再运行 `pnpm memory:index`，生成本地视图。
- 历史任务记录里「用 `pnpm memory:index` 重建 INDEX.md」之类的写法，是当时的做法，保持原样。
- 生成时仍先写临时文件再原子替换。原子替换只保证文件不会半写入；只有读取期间记录没有变化，同一工作区里并行生成才会得到相同的内容。
- 本地索引可能落后于当前分支上的记录，比如切换分支或合并之后。开工时运行一次就能刷新；它从不进入提交，所以落后也不会传给别人。

## 验证

- `scripts/work-memory.test.mjs` 覆盖以下行为：
  - 索引仍是确定的，排序稳定；
  - `--check` 不读取索引文件：索引缺失、或内容与记录不符时，都照样通过；
  - INDEX.md 被 Git 跟踪时，`--check` 失败；
  - 批量核对时，不存在的提交、树和文件内容都失败，失败信息写出引用它的记录 ID；
  - 指向提交的附注标签按其提交通过；
  - 名字多到输出超过默认的 1 MiB 缓冲时，照样能核对。
- 在本仓库上运行 `pnpm memory:index`、`memory:check`、`memory:test` 与 `git diff --check`，并记下检查用时。
