# ADR 0018：滑杆手势只在松手或浏览器取消时结束；捕获丢失不是取消，手势改动须以真实输入验证

- 状态：已接受并实施（产品负责人，2026-09-20）；实施、证据与验证见[任务记录](../work-memory/sessions/2026-09-20-slider-review.md)。本文同时是这次缺陷的复盘。
- 关联：[滑杆交互契约](../slider-interactions.md)（当前行为、取消路径、诊断与验证步骤的归属文档）；[运行时守卫](../runtime-guardrails.md) §10；[ADR 0017](0017-market-close-confirmed-size-ceiling.md) 附录（拖动期间提交锁是同步 ref，不改变按钮外观）。

## 背景：发生了什么

现象：在数量、平仓、止盈止损和杠杆滑杆上用真实鼠标拖动，松手后滑块回到拖动前的位置，数量不变。不是每次都发生。

根因：`TradeSlider` 把 `lostpointercapture` 当作取消。在内嵌 webview（Claude 桌面应用的浏览器面板，Chrome 152）里，真实鼠标松手时浏览器多数情况下先派发 `lostpointercapture`，6–11ms 后才派发 `pointerup`。滑杆在前一个事件上取消了手势并恢复起始值，随后的 `pointerup` 找不到会话，什么也不做。产品负责人的 23 次真实手势里 14 次是这个顺序，全部被丢弃；顺序正常的 9 次全部提交。嵌入方为什么先报告捕获丢失，没有查证，只记录现象。独立的 Chrome、Safari、Firefox 标签页与真实触屏上是否出现同样的顺序，没有验证。

来历（git 可证）：`e4afed7b`（2026-08-11）在杠杆滑杆上加入 `onLostPointerCapture → 取消`，`9af3bb69`（2026-08-19）加到数量滑杆，`178661c3`（2026-09-10）合并为 `trade-slider.tsx` 并把「lost capture」写进契约文档的取消清单。三次的提交说明都是「加固生命周期」。配套单测断言「捕获丢失即取消」，与实现共享同一个没有证据的假设：捕获丢失只会出现在手势被真正打断的时候。缺陷因此带着全绿的测试存在了五到六周。

为什么自动化与我的手工验证都没发现：

- jsdom 里的事件由测试按自己认为的顺序派发，只能证明「给定顺序下的行为」，不能证明浏览器会给出什么顺序。
- Playwright 与 DevTools 协议注入的鼠标事件是 `isTrusted` 的，但不经过系统级的鼠标捕获路径；本次用它们做的全部验证里从未出现先 `lostpointercapture` 后 `pointerup` 的顺序。
- 任务记录里的「在真实页面上验证」实际用的是脚本派发或协议注入的事件。「真实页面」不等于「真实输入」，这个措辞掩盖了没有覆盖到的那条路径。

诊断走过的弯路（如实记录）：

1. 第一次听到「会不会跳回起点」时，我找到了另一个真实缺陷（桌面弹窗 200ms 缩放动画期间 ResizeObserver 误判尺寸变化而取消手势）并修复，没有向报告人确认那是不是他看到的现象，就当作答案交付。
2. 之后按「对齐官方」又做了节流与暂停，仍然是从代码推断可能的原因。
3. 报告人再次报告后，我用注入事件在桌面宽窄两种布局、移动布局、多空两个方向上快拖、慢拖、连续拖，全部正常，仍然无法复现。
4. 转折点是停止猜测：给滑杆加上「上一次手势为何结束」的记录（`data-gesture-end`），在页面里装只读的事件记录器，读报告人自己的真实手势。一次读取就得到了事件顺序与结束原因。
5. 修复后由报告人复测：20 次真实手势全部提交，其中 12 次正是先 `lostpointercapture` 后 `pointerup` 的顺序。

## 目标与约束

- 真实输入下，一次拖动以松手时的值结束；只有浏览器明确取消或编辑上下文结束才丢弃。
- 不放松既有安全边界：手势期间的提交锁、身份/范围/方向变化即取消、`disabled` 即取消、卸载清理、`paused` 语义不变。
- 手势尽量不悬挂，结束后提交锁必须释放。捕获丢失且松手事件没有到达文档时，要靠同一指针之后的移动（决策 3）或保留下来的取消路径（失焦等）结束；没有任何后续事件时代码不会自行结束手势。
- 下一次有人报告滑杆异常时，能从页面上直接读出原因，而不是再猜一轮。

## 决策

1. **`lostpointercapture` 不是取消。** 它只在会话上做标记。结束手势的信号只有三类：`pointerup`（会话仍然有效且未暂停时提交，否则取消）、`pointercancel`（取消）、编辑上下文结束（`disabled`、身份/范围/方向变化、卸载；取消）。其余既有取消路径（窗口失焦、页面隐藏、窗口或控件宽度变化、输入失焦、Esc）保留，见决策 4。
2. **移动、松手与 `pointercancel` 由手势存活期间挂在 `document` 上的监听处理**，不依赖指针捕获。捕获仍然申请，它让指针离开控件时事件继续到达，但正确性不再建立在它之上。
3. **漏掉松手的兜底。** 报告过捕获丢失之后，若同一指针出现不带按键的移动，说明松手事件没有到达文档（例如在 iframe 上方松开），此时提交按键按下期间最后看到的草稿值。这个兜底只在报告过捕获丢失后生效，捕获完好时不把无按键移动当松手。
4. **每条结束路径都有名字并可观测。** 控件在 `data-gesture-end` 上记录上一次手势的结局：`commit`、`unchanged` 或 `cancel:<原因>`，下一次手势开始时清除。新增取消路径必须同时给出：写入这里的原因名、一个说得出的真实触发场景、真实输入下普通手势不会触发它的证据、钉住它的测试。拿不出真实输入证据的「加固」不加。
5. **手势生命周期的改动以真实输入验证。** 记录验证时写明输入路径：脚本派发、协议注入（Playwright / DevTools）还是物理输入。只有物理输入能证明系统级的事件顺序、指针捕获与焦点行为。涉及这些的改动在物理输入验证之前不写「已验证」。
6. **报告的手势缺陷以报告人的场景为准。** 先读 `data-gesture-end` 或装记录器取证，再改代码；找到一个缺陷并修复，不等于修复了被报告的缺陷，要由报告人的场景确认。诊断步骤与记录器脚本见[滑杆交互契约](../slider-interactions.md)。

## 备选方案

| 方案 | 取舍 |
| --- | --- |
| 保留「捕获丢失即取消」，加一个 20–50ms 的宽限期等 `pointerup` | 能修这一次的顺序问题，但把一个没有证据的时间常数写进交互核心；真正丢失捕获且迟迟没有松手时仍要在超时后做选择。未采用。 |
| 完全忽略 `lostpointercapture`，不做标记 | 最简单，能修报告的现象。但捕获丢失后在 iframe 上方松手时，松手事件到不了文档，手势与提交锁会悬挂到下一次失焦，期间点击提交会先触发失焦取消、把数量恢复成起始值再提交，出现「所见与所提交不一致」。未采用。 |
| 像官方终端那样不设任何取消路径，一律以最后的值提交 | 与官方一致，但放弃了身份、市场、方向变化时不得把旧手势写进新上下文的保护，这些保护有实际的资金含义。未采用。 |
| 采用的方案：标记 + 文档级监听 + 仅在捕获丢失后启用的无按键兜底 | 修复报告的现象，不新增时间常数，漏掉松手时在下一次指针移动结束手势，保留上下文保护。代价是移动处理从控件上的 React 处理器改到文档级原生监听，测量脚本与真实鼠标共用指针编号 1 时会互相干扰（测量时要拦掉 `isTrusted` 的移动）。 |

## 后果与边界

- 所有使用 `TradeSlider` 的表面同时生效：桌面与移动下单、市价与限价平仓、止盈止损数量、杠杆与保证金模式弹窗。
- `use-press-and-hold.ts` 也监听 `lostpointercapture`，但它的动作在计时完成时触发，松手与捕获丢失同为取消未完成的长按，事件先后不影响结果，保持不变。
- 保留下来的环境类取消路径（窗口失焦、输入失焦、尺寸变化、页面隐藏）在报告人的 43 次真实手势里一次都没有触发，但它们同样是「多做的健壮性」。今后若 `data-gesture-end` 显示其中某一条在普通手势里触发，按决策 4 重新评估，而不是再加一层补丁。
- 同一轮里顺带确立：表面不得在手势期间移动指针下方的滑杆。桌面下单面板的数量校验提示行在手势期间冻结其有无与高度，松手后再按当前校验结果更新（[下单面板对照](../order-entry-surface-parity.md)）。
