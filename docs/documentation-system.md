# 文档体系设计与维护约定

状态：本轮采用的维护约定。建立日期：2026-09-12。范围：本仓库的设计、工作记忆、参考与交付文档。

## 目标与约束

文档与代码共同构成交付。后来接手的人应能找到系统的目标、边界、为何采用当前方案、如何运行和验证，以及哪些结论尚无证据。设计文档先澄清行为，Reference 准确描述已实现行为，历史记录保留当时实际知道的事情。

现有文档分散在 `docs/`、`features/`、仓库根目录的 review 文件和 `notes/`。本轮保留原路径，避免破坏已有引用；不要求一次性重写旧资料。不把旧方案、源码中的现状或一条测试结果单独当成产品要求。要求与实现发生冲突时应记录差异并修复，不能静默改变文档来掩盖代码缺陷。

## 三类文档

| 类别 | 回答的问题 | 位置与实际入口 | 必须包含 |
| --- | --- | --- | --- |
| 设计文档 | 要实现什么，边界和方案是什么？ | `docs/` 主题契约，例如[桌面网格](desktop-grid-layout.md)、[首次交易](trading-onboarding.md) | 目标、约束、方案、非目标、状态/身份边界、备选方案及代价、验收条件 |
| 工作记忆：原始层 | 当时收到什么、观察到什么、做过什么？ | 保留既有 review/verification 文件；原始证据归档与新任务记录遵循项目工作记忆入口 | 可获得的原始请求、操作及结果、证据位置、失败、限制与后续更正；注明是全文还是摘要 |
| 工作记忆：整理层 | 接下来从哪里继续？哪些结论已失效？ | 项目工作记忆检索入口；[历史与审查索引](../notes/index.md)补充旧资料 | 主题、原始记录链接、当前契约、结论状态、未完成项 |
| 参考与交付 | 系统现在如何工作，如何完成一个任务，变更是什么？ | 主题 Reference、[教程](tutorials/local-development.md)、[Changelog](../CHANGELOG.md)、[ADR](adr/README.md) | Reference 的接口/状态/边界；教程的步骤及预期结果；发行说明的用户影响；ADR 的决策及利弊 |

ADR 属于交付记录，也为未来设计提供依据。现有文档可以兼有设计和 Reference 两种职责，但必须分清“当前行为”和“拟实施”；不要为凑目录复制整份规范。

两层指逻辑职责，不限制物理目录数量：原始证据、本次任务摘要和生成索引可以分别存储。项目的 `docs/work-memory/` 入口负责持续任务归档、元数据、本地证据工具和索引命令。`notes/` 只补足已有原文的目录及文档审查记录，不另建采集脚本或第二套生成器。

## 导航与状态

[文档地图](README.md)按任务提供入口；[工作索引](../notes/index.md)管理证据和历史。`AGENTS.md` 仅保留稳定约束及文档链接，不放单次调试结论、提交号或测试数字。

新增或实质改写的文档在开头说明范围与状态。适用状态包括：拟议、已采用/已实现、历史记录、被替代、待验证。日期表示该文档实际审查或发生变更的时间，不凭提交时间重建原始决策日期。回溯补写的 ADR 明确写“回溯记录”。

当前契约和历史材料冲突时，以明确的当前要求及对应实现证据进行复核。SDK 快照与外部网页摘录仅供检索；协议变更仍按 [SDK 核对流程](hyperliquid-sdk-reference.md)查询当前官方资料和锁定声明。文档地图的“历史”标签不等于其中所有内容无效，也不表示已逐行复审。

## 工作记忆的完整性

完整原始记录与整理索引分别维护，索引不能替代原文。已有原始材料保留在原路径；有完整对话/工具导出时记录其出处并保留安全版本，不用摘要冒充全文。未获得的历史对话标记缺失，不按 Git 日志补造。

任务记录至少保存：原始需求、起始提交与工作区状态、影响范围、事实发现、修改清单、实际执行的验证及结果、未决问题。记录更正使用追加条目；当前 Reference 可以直接更新，历史记录通过索引或追加说明链接后续结论。

钱包私钥、Agent key、配对密文/票据、认证令牌、环境变量值、个人账户信息不进入仓库。需要脱敏时使用明确的 `[已脱敏：类别]`，说明原因并保留与结论相关的非敏感事实。“完整”不要求公开敏感原文。工作日志不是内部思维推演，记录可核验的请求、动作和证据即可。

每个有实质变更的任务结束时更新原始层记录与索引；持续进行的工作在交接、阶段结束及每周整理一次索引。任务工具和定期维护以项目工作记忆入口为准；本轮文档审查没有另行创建后台任务。

## 从设计到交付

1. 改动前查地图与相关契约，写明目标、非目标、关键状态和验证方式。小型文案修正不需要独立设计文档。
2. 改动身份、签名、资金、订阅、布局所有权等系统边界时，先更新设计；存在长期取舍时增加 ADR，链接已有实现细节。
3. 实现期间保留证据，区分“计划运行”“实际运行”“失败”“未运行”。更改契约时同步对应测试和 Reference。
4. 交付前更新用户可见的 Unreleased 说明及受影响教程。纯维护变更可只写工作记录，不需要虚构产品发布条目。
5. 检查链接、路径、命令、环境变量名、文档状态和相关代码。修改文档不自动要求全量应用构建；运行文档中新增的可执行示例或适当的针对性验证，并如实写出限制。

验收标准：入口能找到新文档；当前说明不与本次核对的代码和要求冲突；设计有边界与代价；教程有预期结果；执行结果有证据；未完成事项留在索引；历史与发布状态明确；同一变更提交包含相应文档。

## 取舍与边界

- 采用“保留原文、增加索引”，减少迁移噪声并保留历史引用；代价是目录暂时不完全统一，需要维护导航。
- 当前 Reference 可持续修订，历史记录保留原结论并追加更正；代价是必须显式链接替代关系。
- 不把所有细节复制到 ADR/README。它们负责入口和决策，主题文档负责完整契约；代价是读者需沿链接阅读，但减少多份事实漂移。
- 这轮是文档审查，不能替代完整代码审计、实时外部协议复核、生产部署或真机验收。已知证据缺口见[工作索引](../notes/index.md)。
