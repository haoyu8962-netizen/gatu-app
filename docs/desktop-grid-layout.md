# Desktop grid layout

The desktop workspace uses one React Grid Layout instance with stable panel keys. The layout starts at 1001px, uses 14 columns through 1420px, and uses 16 columns above 1420px. Grid rows are 30px with 3px gutters and outer padding; keep `margin` and React Grid Layout `containerPadding` aligned, because the latter is geometry rather than CSS padding.

Default spans live in `apps/terminal/src/config/desktop-grid-layout.ts`. The 16-column (lg) layout uses a `10 / 3 / 3` upper row (chart, market data, trading panel) and a `13 / 3` lower row (account table, account information). The 14-column (md) layout uses two columns since [ADR 0011](adr/0011-desktop-md-stacked-right-column.md): the chart column spans 10 columns with the account table (14 rows) beneath it, and the 4-column right column stacks the trading panel (20.6 rows), the order book (20.4 rows) and the account information (14 rows), for a 55-row grid that scrolls with the page. Changing default geometry incompatibly requires bumping `DESKTOP_GRID_STORAGE_KEY` (currently v12).

The grid underlay is the `bg-grid-container` token (`#F1F3F6` behind white panels in the light theme, `#1B2429` behind `#0F1A1F` panels in the dark theme). React Grid Layout itself stays transparent so the underlay shows through every gutter; do not replace that separation with panel borders.

The real desktop surface uses `DesktopTerminalFrameView`: a `min-h-dvh` flex column
with horizontal overflow hidden, `pb-8` for the fixed footer and `pt-14` (or the
testnet banner offset) for the fixed header. Before the market is ready, real
TopNav/FooterBar and runtime banners surround an empty `min-h-0 flex-1
bg-grid-container` busy workspace. Grid measurement also leaves the workspace
empty until its width is known. Chrome remains mounted through readiness; the
prerendered body has no grid or chrome. See [ADR 0010](adr/0010-blank-until-ready-startup.md).

## Shared boundaries

- Favorites and market information remain above the chart at both breakpoints.
- lg: the chart, market-data panel and trading panel share the upper area's bottom boundary. The account table and account-information panel share their top and bottom boundaries; their common height accommodates both panels' minimum height and the account's natural content height.
- md: one boundary is shared across columns. The chart column bottom, the trading panel bottom, the account table top and the order book top coincide; the account information starts at the order book bottom. The account table height is independent of the account information, and account content growth only extends the account information and the page. Width handles move the single column boundary (left column at least 7 columns, right column at least 3); the chart's bottom handle moves the shared boundary, and the order book's bottom handle only changes the order book height. The topology is selected from the active column count, which React Grid Layout passes to the compactor.
- Resizing a vertical boundary changes the whole affected area. Resizing a column boundary updates neighboring columns while preserving the configured minimum and maximum widths. Panels must not be pushed into another vertical tier to resolve a horizontal resize.
- Apply these rules through the same compactor used by React Grid Layout, content measurement, resizing and saved-layout restoration. A correction applied only after a default vertical compaction is insufficient because the library compacts again during rendering and resizing.

## Height ownership

- Persist user-selected geometry in grid units. Keep observed natural content heights separately, per breakpoint, and derive the displayed geometry from those inputs.
- The upper area's height comes from user-selected grid geometry and panel minimums. Order type, TP/SL, validation feedback and translated form content must not change this boundary. At lg the lower area's height is at least its user-selected height, both account-panel minimums, and the account's natural height; at md only the account information takes its natural height.
- Account content growth may expand the lower area; account content shrinkage must allow it to return to the user's size. Trading form content never sets grid minimums. Never feed a stretched panel height back into natural content measurement or save it as a new user preference.
- Measure actual content inside Suspense boundaries. Loading fallbacks and detached nodes must not change persisted geometry.
- Measure natural content in a separate, non-stretched layer. A `height: 100%` or auto-margin expansion must not become a new content minimum.

## Persistence and verification

Validate saved geometry and preserve current constraints and panel identities. Restore shared boundaries from valid saved user geometry. The v11-to-v12 migration keeps the lg rules of the earlier v10-to-v11 migration (valid column widths and user-resizable chart, market-data and account-table heights are preserved; measured trading/account heights and derived vertical positions are discarded) and resets md to the new stacked default because its topology changed. Older storage versions are discarded without being read. Restored md geometry must also keep one consistent column boundary; inconsistent, out-of-bounds or colliding md storage falls back to the default. Reset must remain available.

Regression checks must cover both desktop breakpoints, repeated breakpoint changes, content growth and shrinkage, user resizing in both directions, saved-layout restoration, and loading-to-content transitions. Inspect actual React Grid Layout bounds in a browser: paired boundaries may differ by at most one CSS pixel, panels must not collide, and repeated measurements must settle without growth loops. Shared layout changes must not remount panel contents. Browser drag tests must also fail on runtime exceptions; compile the drag dependency's debug flag to `false` in both application and fixture builds so resizing does not depend on a browser `process` global.

## Mobile order-entry height

The embedded mobile form and compact order book share a viewport-based minimum height: `clamp(370px, 60svh, 480px)`. This is a floor, not a fixed height or content ceiling. The form's natural content determines any additional height; the book stretches alongside it and account panels follow below. Keep the book out of intrinsic height calculation so its measured row count cannot feed back into split sizing.

Use the surrounding mobile page as the single vertical scroll owner. The embedded form, including its order toolbar, complete fields, summary and action feedback, must not have an independent vertical scroll viewport. Short viewports and open keyboards may require page scrolling to reach the action; no content may be clipped. The standalone form retains its existing scroll behavior.

Order-type switches, expanded controls, locale changes and requested-action feedback may change natural height. Preserve mounted input state and subscriptions. Do not create hidden measurement copies, order-type height tables, quote-driven height state or ResizeObserver feedback loops. Retain all TWAP conditions, summaries, fees and touch targets; keep ordinary field spacing compact before allocating more height.

Verify 320px, 393px and tablet widths, all eight real order types, advanced TWAP values, TP/SL, long action feedback and keyboard reachability. Assert no embedded vertical overflow, aligned book/form bottom edges, account panels below the split, and shrinking back after tall content is removed. Repeated market-value updates must not progressively grow the layout. Desktop grid height ownership remains unchanged.
