- **V-P2：同文件函数经别名或作为对象方法调用后，返回值来源丢失。** 例子有 `const readIntl = getIntl; readIntl()` 和 `helpers.getIntl()`。原因是返回值只按被调函数自身的名字查找。编译产物切换语言后仍输出旧语言。
- **B-P2：展开 `useLingui()` 的结果再解构会丢失 `i18n`。** 例子是 `const context = { ...useLingui() }`。原因是展开只复制对象字面量里已知的成员，不包括角色隐含的成员。
- **V-P3：展开后同名成员被合并而不是被替换，造成误报。** 例子是 `{ ...box, intl: { locale: "en" } }`。

处理办法是把函数也当作抽象值，值上可以带「调用后返回什么」：

- 函数声明、函数表达式、箭头函数、对象方法与 getter 都在这个结构上传播；
- 调用时取被调用值的返回值，所以别名调用、方法调用都能跟上；
- 对象字面量按源码顺序构建，后写成员替换先写成员；
- 展开时复制已知成员，并补上角色隐含的成员，例如 `useLingui()` 结果的 `i18n`；展开 i18n 对象本身只复制普通值，不当作稳定对象传播。
- 原先单独的「返回值表」并入这个结构。
- `call`、`apply`、`bind` 调用已写进「不跟随」清单。
- 语言契约在第 7 轮后每一轮都被找到一种新的数据流组合。这类组合在静态检查里没有尽头，所以在「不跟随」清单末尾补了一条兜底说明：清单之外的任何数据流都不跟随，契约只是覆盖所列写法的词法守卫，不是证明；在组件顶层先写 `const locale = i18n.locale;` 才是始终安全的写法。第 16 轮请审查方专门评估这条兜底是否如实、可接受，判级规则不变。
