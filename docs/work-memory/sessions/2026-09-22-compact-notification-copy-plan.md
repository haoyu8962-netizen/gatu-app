# 交易通知精简文案与移动端方案

状态：拟议，未实施。基线 `a999806b`，工作区开始时干净。用户希望借鉴官方普通下单「订单已提交 → 数量、币种、买卖方向与平均成交价」的通知，进一步精简项目文字并适配移动端。用户所述官方提示是本轮输入，不作为代理本轮重新下单捕获的证据；以下例子均为模板或合成数值。

## 背景与范围

现有 OrderToast 同时展示订单类型、市场、方向、独立状态、Size、价格和 TP/SL，多行信息有重复；错误状态还可能叠加长状态说明与错误正文。建议普通操作优先只展示用户需要知道的结果，市场/方向/数量不重复列标题。复用现有全局 Sonner 和刚修复的展示生命周期，双端共用状态、内容来源与翻译模板。

本轮只读审查与方案记录，不修改应用、通知时长或交易行为。当前规范仍由 [全局操作通知](../../trading-notifications.md)维护。

## 结论与依据

### 精简文案

| 已证实的阶段/结果 | 建议文案模板 | 边界 |
| --- | --- | --- |
| 本地准备、签名、发送或等待回包 | `正在提交…`；并发时附市场名 | 当前 pending 在订单计划验证及 submitOrder 之前建立，不能直接改成「已提交」 |
| 明确已受理且挂单 | `HYPE 订单已提交`；必要时附 `买入 1 HYPE · 限价 $100` | 只表示接受，不表示成交；不强制让快速成交先停留一段「已提交」 |
| 有真实成交量及均价 | `已买入 1 HYPE · 均价 $100` | 成交回包为依据，卖出同理；报价单位来自市场，不全局硬编码美元 |
| 只确认 filled 状态，无实际量价 | `HYPE 订单已成交` | 省略未知量价，不能用请求量/价格补齐 |
| 有实际部分成交量 | `部分成交 0.4 / 1 HYPE`；有依据时补均价 | 未成交部分的后续状态需另有证据，不能一律声称继续挂单或取消 |
| 回包不明确，正在核对 | `确认中，请勿重复提交` | 保留后台对账与业务锁 |
| 超时仍不明确 | `结果待确认，请先核对订单` | 不显示失败，不暗示立即重试 |
| 明确失败 | `HYPE 下单失败 · 保证金不足` 等已知简短原因 | 只映射已知原因；未知错误保留准确正文并允许换行，不删除唯一诊断信息 |
| 批次结果 | `已提交 3 笔平仓单` 或 `平仓完成 2/3` | 按接受/真实成交/新鲜仓位清空证据分别表述；保留异常市场明细，不将整批未知美化为成功 |

普通成功取消重复的「委托 / 已成交 / 数量」标签；状态由完整短句和图标表达，不只靠红绿颜色。TP/SL 价格不在每张成功卡重复；主单成功但附属单失败必须保留独立的简短结果，不能一并隐藏。撤单、改单、杠杆等继续用动作加结果，如「订单已撤销」「杠杆已设为 10x」。TWAP 创建成功表示已创建，不能套用普通成交句。

### 移动端

使用同一语义内容按宽度排版。桌面允许一句显示 `已买入 1 HYPE · 均价 $100`；手机自然分成两行：第一行 `已买入 1 HYPE`，第二行 `均价 $100`。普通单目标是最多两行主体，长币种、翻译和错误应允许增加行数，不能通过省略号截断关键数量、价格或原因。

沿用 <=1000px 布局断点、左右安全间距和底部导航上方的全局堆叠，不另建移动通知系统。图标、关闭控件及数量/价格的可读字号保留，优先删重复标签，不缩小字体。批次默认短汇总，但失败/未知子项仍可查看；若引入「查看订单/仓位」操作，应复用现有页面入口，不能宣称已有完整持久通知中心。此次建议不改变既定 3 秒结果、5 秒成功或 pending/confirming 常驻等时长规则。

### 必须补齐的数据

`use-order-submit.ts:181-200` 把格式化请求量及 input.price 写入 queue.size/price；成功分支第 299-305 行只记录 outcome，没有保存实际成交量和均价。OrderToast 第 84-88 行因此展示原始 size/price。现字段不能仅改标签成为「成交均价」。官方 Exchange 文档的 `filled` 回包提供 `totalSz`、`avgPx`、`oid`。

建议独立增加可选 execution 摘要（实际成交量、均价、订单关联及证据来源），保留请求字段原义；domain 纯函数按提交订单和响应位置验证、提取。普通单只处理主单；Scale 仅对同市场同方向的实际成交作数量加权，TP/SL 不混入主单，金融运算用 Big.js。通过现有 `onResponse` 扩展点在 tracker 保存 pending feedback 前补入摘要，同时更新 metadata schema，保持坏显示字段不能破坏合法交易记录的现有规则。

WS/REST 的 order-status 对账只有状态时，继续使用无量价的短句。近期成交列表不是某订单完整成交证据；若后续要求挂单成交也总能显示均价，需要单独设计订单关联、去重、累积范围及历史缺口恢复，不能在本次纯文案层臆算。

建议实施顺序：先补数据及部分成交判定，再建立显式接收翻译依赖的共享呈现函数，最后缩减 OrderToast 内容并验证两端。呈现层不做金融计算；locale 变更重译同一任务，不重发或重建通知。覆盖单单全/部分成交、已受理挂单、拒单、未知、批次混合结果、TP/SL 主从、缺失/损坏成交 metadata、恢复、快速状态更新与语言切换；浏览器验证 390/800/1000/1280px、两主题及长翻译。
