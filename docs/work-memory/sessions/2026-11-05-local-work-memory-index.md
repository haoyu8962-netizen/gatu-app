# 工作记忆索引改为本地生成、不入库（ADR 0049），手册新增「不默认开 Auto-fix」

## 背景与范围

同步记录，未取得任务标识。时间都是 UTC+8。

2026-11-05，晋升 PR #155 开出后，我按应用的默认流程提议为它开启 Auto-fix。运营方问：

> 如果我开启 Auto-fix 就会不断的循环 修复 推动 跑CI 因为永远会产品 修复 你没发现吗？

核对后，我承认这一点成立：
- 它与 2026-10-12 和运营方约定的「一个代码 PR 尽量只推一次」冲突；
- 循环的主要来源，是生成并入库的 `docs/work-memory/INDEX.md`。

我把根治办法提议成一个单独的任务。运营方回复：

> 在这里完成此任务：“消除 INDEX.md 在并行 PR 间的冲突”

范围：
- 改动：工作记忆索引的入库方式、检查脚本、相关说明；在手册里记下 Auto-fix 的偏好。
- 不变：任务记录的格式、历史记录的正文、CI 工作流。

## 结论与依据

**证据**（2026-11-05 在 `dev` `76983456` 上读取）：
- INDEX.md 有 759 行、约 386 KB。每条记录的完整摘要按议题重复出现，后面还有一张日期表。
- `memory:check` 要求索引与生成结果逐字相同，所以几乎每个 PR 都重建并提交它。
- 新记录插在各议题的最前面，所以两个开着的 PR 常常改在同一处或相邻的行上。
- 实际冲突：
  - #153 在 #151、#154 先后合入后各冲突一次；
  - #134 冲突过两次，#149 一次，见各自的任务记录；
  - 当时 #152、#153 与晋升 PR #155 都改了这个文件。
- `.github/workflows` 里没有任何工作流运行 `memory:*`。
- 本记录之前的记录共引用 890 个不同的提交。原检查逐个运行 `git cat-file -e`，一次约 18 秒。

**方案**：见 [ADR 0049](../../adr/0049-local-work-memory-index.md)。
1. INDEX.md 从 Git 中删除，写进 `.gitignore`，改为 `pnpm memory:index` 在本地生成的视图，内容与格式不变。
2. `memory:check` 不再读取索引文件，只做三件事：
   - 校验全部记录；
   - 确认索引能正常生成；
   - INDEX.md 仍被 Git 跟踪时失败。
3. 提交引用改为一次 `git cat-file --batch-check` 批量核对。
   - 判定与原来相同：解析不到或不能剥离为提交的名字都失败；指向提交的附注标签照样通过。
   - 失败信息写出引用它的记录 ID。
   - 输出缓冲随名字数量放大。

**未采用的方案**（理由详见 ADR）：
- 合并后由工作流重建并推送 `dev`：要改 GitHub 设置，还会直接推送 `dev`；
- `.gitattributes` 的合并策略：不能依赖 GitHub 在 PR 上使用它，`union` 还会把新旧两行都留下；
- 改格式：两个 PR 在同一位置插入新记录，照样冲突；
- 只在每周整理时提交索引：库里的索引最多旧一周，而且本地重建的文件容易随 PR 一起提交回去；
- lefthook 钩子自动重建：每次切换分支都要运行，旧分支上的记录有问题时会反复报错。

**同步更新的文档**：
- `AGENTS.md`「Operator collaboration」与「Work memory」：开工时先运行 `pnpm memory:index`；改动记录后跑 `memory:check` 与 `memory:test`；索引不提交。
- `docs/work-memory/README.md`：三层记录表、开始任务、完成任务与检查、并行生成的说明、每周维护。
- `docs/agent-handbook.md`：
  - 开始任务第 2 步；
  - 集成 PR 的冲突说明；
  - 新增「不默认开 Auto-fix」一条：运营方明确要求才开，晋升 PR 永远不开；问到 CI 时查一次，修复攒成一次推送。
- `codex-onboard.md` 与 `docs/across-reference.md`：入口里补上先生成索引。

## 验证与限制

基线是 `dev` `76983456`，分支 `claude/local-work-memory-index`。

- `node --test scripts/work-memory.test.mjs`：11 项通过。相对原有测试的变化：
  - 新增「索引被 Git 跟踪时检查失败」；
  - 改写「检查不读本地索引」：索引缺失或过期时都照样通过；
  - 补上树与文件内容作为提交引用时失败，失败信息带记录 ID；
  - 新增「附注标签按其提交通过；失败信息写出真正引用它的那条记录」；
  - 新增「名字多到输出超过默认 1 MiB 缓冲时照样能核对」，用 25,000 个不存在的名字。
- 变异检查：八个变异全部被测试抓到。变异是临时改动脚本，跑测试，再恢复原文件：
  1. 检查恢复比较索引；
  2. 允许索引被跟踪；
  3. 批量核对接受任意行；
  4. 跳过批量核对；
  5. 失败信息不带记录 ID；
  6. 去掉放大的输出缓冲；
  7. 不再剥离为提交；
  8. 失败信息固定写第一条记录。
- Codex CLI 只读审查（`gpt-6-astra`，low）给了 8.4/10，五项发现，核实后都成立并已修正：
  - P1：批量核对沿用默认的 1 MiB 输出缓冲，约两万个提交引用就会失败（Codex 用 25,000 条查询实测得到 `ENOBUFS`）。改为缓冲随名字数量放大，并补回归测试。
  - P2：「不是提交都失败」不准确，指向提交的附注标签会通过，与原实现相同。改了措辞，补上测试。
  - P2：树的断言没有带记录 ID，也没有测过多条记录时归属对不对。已补。
  - P2：原文说「PR 不会触发检查」，漏了一个前提：`Claude Code Review` 没有路径过滤，是靠手动停用才不运行。已改。
  - P3：ADR 里「就冲突」「办法只有一个」「并行生成内容相同」说得太绝对，已收窄。
  - Codex 在它的沙盒里只跑通 2 项测试，其余 7 项因为不能创建临时夹具而失败，不是行为失败；在沙盒外 11 项全部通过。
- 修正后的窄范围复审给了 9.4/10，五项都已修复。
  - 它用只读探针确认：默认缓冲下 25,000 个名字会得到 `ENOBUFS`，修正后得到带记录 ID 的错误。
  - 它另外指出两处绝对说法（「都会冲突」「一定在同一处」），已改为条件性表述。
  - 它没有运行需要临时仓库的测试与变异，所以「11 项通过、八个变异被抓到」是作者自己运行的结果。
- 在本仓库上实测：
  - 取消跟踪之前，`node scripts/work-memory.mjs --check` 按预期失败，提示 `INDEX.md must not be tracked`；
  - `git rm --cached` 之后，`--write` 用 0.51 秒生成 759 行的本地索引，`--check` 用 0.30 秒通过，改动前约 18 秒；
  - `git check-ignore` 确认 INDEX.md 已被忽略；
  - `git diff --check` 通过。
- 这次改动只碰文档、`scripts/work-memory*.mjs` 与 `.gitignore`，不在五个按路径过滤的 CI 工作流的 `paths` 里。`Claude Code Review` 工作流没有路径过滤，手册记录它已手动停用；本次没有核对远端状态。

**未覆盖与限制**：
- 没有在 GitHub 上实测 `merge=union`。那是未采用的方案，结论依据是：GitHub 不能配置服务器端的合并驱动，并且 `union` 本身会保留双份。
- 批量核对对「有歧义」的短提交号判失败，与原来一致；但本仓库里构造不出歧义，测试没有覆盖这一支。
- 没有改动其他会话的分支。
