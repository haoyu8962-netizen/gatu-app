# 只减仓修复方案

状态：2026-09-21 已实施；实施基线 `0fafbc7f`，最终检查与限制见[实施记录](work-memory/sessions/2026-09-21-reduce-only-implementation.md)。以下保留制定时的设计与验收标准，实际交付范围见下节。2026-09-21 制定时的代码基线为 `7342b7f3`。本方案承接[首次审查](work-memory/sessions/2026-09-21-reduce-only-review.md)，有仓位官方终端实测见[补充记录](work-memory/sessions/2026-09-21-reduce-only-official-followup.md)。

## 实际交付

共享容量模型、桌面/手机表单、通用校验器、八类主单执行守卫、精确数量来源和保证金占位均已接入。百分比先生成精确基础币量，确认到 SDK 请求复用该字符串；Scale 合计检查，normalTpsl 只检查主单。零开仓余额不再强制跳转充值，所有会话、市场和数据可用性门槛保留。持仓订阅拒绝错 owner、非法数量和畸形/重复身份快照。

未实施额外的强平价估算、小额平仓最低价值豁免或真实账户订单；官方现场观察仍只覆盖此前补充记录。真实签名、成交、零可用余额实盘和手机真机不属于已通过的自动化验证。

## 目标与范围

使订单输入、百分比、Max、表单校验、确认数据和最终提交使用一致的只减仓语义：只能减少当前市场既有的反方向持仓，不能新增风险；草稿、展示与发送的基础币数量一致。覆盖桌面与手机、普通永续与 builder 永续，以及市价、限价、四类条件单、TWAP 和 Scale。

本轮不改外部钱包/邮箱签名、Agent 授权、下单协议、现货能力、杠杆设置、页面几何或历史订单。沿用 SDK `0.33.3`；不增加新的 Reduce Only 持久化偏好，不自动切换买卖方向，不生成或签署真实订单。独立仓位平仓弹窗继续遵守既有确认数量上限契约，不顺带重构。

## 官方实践：已观察与限制

在用户已登录且有多头仓位的官方 HYPE 终端上，只修改表单草稿，得到以下结果。为避免记录个人账户信息，下表只写比例和关系。

| 操作 | 现场结果 | 我方拟采用行为 |
| --- | --- | --- |
| 市价卖出、只减仓、50% | 基础币数量等于持仓的一半 | 以可减仓基础币量为分母 |
| 市价卖出、只减仓、100% | 基础币数量等于当前持仓 | 精确按 szDecimals 生成最大可减仓量 |
| 输入比持仓多一个最小数量单位 | 保留输入，按钮提示“仅减仓太大” | 保留输入、字段校验、禁用提交；不自动截断 |
| 切回买入，等待页面更新稳定 | 数量草稿保留，按钮提示“仅减仓太大” | 不自动反转方向；上限为 0，给出方向不匹配的输入反馈 |
| 关闭再开启只减仓 | 数量保留；比例基准与保证金摘要切换 | 派生上限与比例，不用 Effect 写回数量 |
| 有效只减仓 | 所需保证金显示 N/A；可用余额行仍保留账户数据 | 保证金显示既有数值占位；余额和可减仓量分开建模 |
| 切为 USDC 数量单位 | 输入转换为金额；50% 按持仓规模生成金额 | 共用明确价格来源和精度规则，协议 s 仍是基础币字符串 |
| 限价只减仓输入超额基础币数量 | 按钮提示“仅减仓太大”，保证金 N/A | 与市价共享持仓上限校验 |
| TWAP 只减仓 | 50% 得到半仓，超额输入显示上述提示 | 共用减仓容量，另保留 TWAP 时间及最低名义价值校验 |
| Scale / 止损市价切换 | 数量、比例与只减仓草稿延续 | 保持共享草稿；本次没有完成这两类订单所有字段或测试提交 |
| 切换至无持仓市场 | 当前仓位为零；100% 不生成数量，按钮仍提示超额 | 只有完整成功快照才判定无仓位；无仓位不可只减仓 |

观察只证明表单表现。官方按钮未设置原生 disabled 属性，不能仅由 DOM 的 isEnabled 判断能否发单；本次没有点击动作按钮来验证其内部提交拦截。金额模式下受价格变化、数量精度和舍入影响，输入金额与订单价值不一定完全相同，不把一次截屏当作其精确换算算法。

本次没有空头账户、零可用余额持仓、真实撤单/成交、组合保证金和手机真机测试。零余额问题仍是源码与合成案例确认的边界，不升级为官方实测结论。官方部分减仓会估算剩余仓位强平价；我方本轮保留现有“不支持该估算时用占位”的行为，不扩展清算模型。

## 设计与决策

### 1. 单一减仓容量模型

在 `domain/trade/order/` 增加纯函数，输入有效 reduceOnly、买卖方向、市场身份与原始 signed position 字符串、持仓快照状态/身份/receipt time、szDecimals。复用既有持仓订阅，桌面与手机从同一映射得到数据；不另建订阅或把 active 当首帧完成。

返回明确状态而不只返回一个数字：普通模式、持仓不可判定、确定无仓位、方向错误、可减仓，以及精确基础币上限。持仓不可判定包括缺帧、错误、陈旧、owner/network/coin/dex 不匹配或非法数字；不能转换为零仓位。完整成功快照没有该市场持仓时，才发布确定的零。

| 持仓状态 | 买入只减仓 | 卖出只减仓 |
| --- | --- | --- |
| 多仓 | 方向错误，上限 0 | 上限为绝对持仓量 |
| 空仓 | 上限为绝对持仓量 | 方向错误，上限 0 |
| 已确认无仓位 | 不可减仓 | 不可减仓 |
| 持仓不可判定 | 不可操作，保持被动数据占位 | 不可操作，保持被动数据占位 |

所有容量、百分比、批量合计与数量比较用 Big.js；保留十进制字符串直到格式化，不能先 `Number(position.szi)` 再作为安全上限。上限按资产数量精度向下量化。只减仓上限不乘杠杆，也不使用账户价值、可用余额或普通 maxTradeSzs 替代。

### 2. 表单、比例和草稿

将 effective reduceOnly 和持仓上下文接入 `useOrderEntryData` / `deriveOrderEntry`；在 `trade-panel.tsx` 与 `mobile-trade-view.tsx` 中先解析持仓上下文再调用共享推导，避免在两个组件复制金融计算。

- 普通订单继续使用原有权威 activeAsset 容量。只减仓的 size Max 和百分比使用减仓容量；顶部可用余额保持原账户语义。余额行如果仍承担 Max 点击动作，也必须使用同一个有效数量上限，不能再从余额独立计算。
- 切开关/方向保留数量输入、订单类型和单位，重新派生上限、百分比与错误。手动超额值不裁剪；拖动/点击比例时才写入新数量。错误方向/无仓位时比例控件不可生成数量，但开关与方向必须仍可操作，避免锁死恢复入口。
- 将“身份和数据不可用”“不能新增仓位”“只减仓输入错误”分开。`availableBalance <= 0` 不能无条件禁用只减仓开关或已验证的减仓数量输入；成功快照的数值零与获取失败仍严格区分。
- passive 数据缺失不显示原始错误或按钮状态文字；用户选择错误方向或输入超额数量，可在字段附近给明确反馈。提交按钮保持本项目静态动词，禁止照搬官方“仅减仓太大”作为按钮文案。
- 保留现有 slider 暂停、指针结束、数量校验行高度规则及 shared draft revision/reset；不通过重挂载表单或新增 Effect 改写数量。语言切换保持草稿与协议值。

金额模式必须有显式换算不变量：同一次百分比选择先计算精确基础币目标，再按当前模式展示；100% 的基础币目标等于量化后的可减仓量。展示金额的舍入不能再次反算成更大的基础币请求，也不能让同一确认展示一种数量却发送另一种数量。若为避免往返舍入必须扩展草稿，仅增加与 market/side/mode/revision 绑定的临时数量来源；手动输入或上下文改变时失效，不新增本地持久化。价格沿用既有选价契约，确认时冻结实际基础币 s。

### 3. 校验器与最终执行守卫同时修复

将当前仅面向 `usesTriggerPrice && reduceOnly` 的持仓检查提取为通用只减仓验证。触发方向仍保留在条件单验证器。不要只改显示层或只给 SDK 的 r 加标记。

表单和 Exchange 执行前均检查：当前精确 owner、市场/网络/dex 身份、成功且未过期的持仓快照、非零仓位、减仓方向、正且合法精度的数量、数量不超过当前可减仓量。最终检查使用请求里的 `b/r/s/a` 与最新上下文，而不是只看 React 里某个 checked 值。

- 市价、限价、条件单、TWAP 使用同一持仓安全规则；原有实时价格、限价/触发价、TWAP 运行时长和最低名义价值规则继续生效。本次不新增小额平仓最低价值豁免。
- Scale 检查同批主订单的基础币数量合计，而非逐个都小于仓位就放行；不得用预期的相反方向成交相互抵扣容量。
- 普通容量检查继续作用于非减仓主单；减仓主单用持仓容量检查替代普通开仓容量数值比较。原有会话、地区、市场、账户模式、数据 freshness 与必要上下文成功条件全部保留，不把 r=true 当免检凭证。
- 复用 `getPrimaryOrders` 区分 `normalTpsl` 父单和附带保护子单：不可把尚未成交父单的保护子单当成当前独立减仓请求，也不能把父子数量相加。保持既有 grouping 和 TP/SL 草稿语义。
- 不擅自把所有既有独立 reduce-only 挂单从当前持仓扣除，也不声称本地能预判撮合执行顺序；有争议的服务端规则另行核对。
- 确认后仓位缩小、消失、翻向或变旧时，拒绝旧意图并提示重新确认；仓位变大时，仍只发送原来确认的数量。不静默缩单、扩单或自动重试。
- 普通 `orders[].r=true`、TWAP `twap.r=true`、基础币字符串 s 保持不变；继续逐项解析拒绝/成交/挂单结果，不把顶层 status=ok 当作全部订单成功。

### 4. 摘要与文案

让 `getOrderMetrics` 的保证金结果可表达“不适用”，同步桌面、移动及确认摘要的类型和显示；只减仓显示现有 `—`，不显示 $0、开仓保证金或被动错误词。普通订单保证金计算保持原样。订单价值、手续费和滑点仍有意义，保留计算。

错误信息区分无持仓、方向不匹配、超过可减仓量、提交时持仓变化；渲染订阅 locale，helper 显式接收翻译依赖。发送 `r=true` 不应被描述为保证成交。

## 验证标准

1. 域测试：多头/空头、买/卖、零/缺失/陈旧/错误/身份不匹配、负数/NaN/精度边界；0/50/100%、手输超额、base/quote 单位、无新增可用余额、有普通容量但无仓位。
2. 八类订单参数化表单测试：正确方向可用、错误方向/超额不可提交；普通订单和 spot 不回归；切订单类型、开关、方向、语言和断点保留有效草稿。
3. 执行测试用合成账户及 mock transport：错误场景不调用 SDK；正确请求 r=true、b 正确、s 为预期字符串；确认后仓位增减/翻向/快照过期，以及 Scale 总量、附带 TP/SL、TWAP 持久跟踪与取消路径。
4. 确认数量不变量：50%/100% 按选定快照生成，base/quote 切换及价格变化后展示与确认/请求一致；仓位增加不扩大已确认订单，仓位缩小不静默裁剪提交。
5. 真实组件浏览器夹具：宽桌面、1001–1420px 紧凑桌面、375px 手机，普通与零余额的可控合成场景；不使用真实账户故障注入。Vite 缓存与应用开发服务分离。
6. Biome 检查变更 TS/TSX、terminal typecheck、AGENTS 对应 desktop/order-entry 与 i18n 组；因跨输入/验证/执行/摘要执行完整 terminal Vitest。根据改动运行现有桌面/手机 all-orders Playwright，并增加减仓场景。所有结果绑定修复后的实际提交，不沿用上轮 176 项审查结果。
7. 文档更新后运行 memory:index/check/test 和 diff 检查；本地提交，不自动推送或发布。真实签名、撮合超额处理、零可用余额实盘边界和手机真机属于独立验收，未执行时必须保留限制。

## 备选与取舍

- **只修复开关或 r 字段**：字段已经正确，不能解决数量、方向或错误禁用。
- **只把 maxSize 改成 min(普通容量, 持仓量)**：仍可能把新增风险容量错误用于减仓，且无法表达未知快照或错误方向。
- **勾选后自动改方向并裁剪数量**：会无声改变意图，官方现场也保留超额草稿，故不采用。
- **完全依赖交易所拒绝**：增加无效签名/请求，前端也无法解释大小变化，故不采用；交易所 r 仍作为最终协议保护。
- **删除全部可用性检查**：会把陈旧或错账户数据视为可用，故不采用。
- **同时重构强平价或添加小额平仓豁免**：证据和范围不足，留在本任务之外。
