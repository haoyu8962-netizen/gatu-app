## Style & UI Guide

### Border Colors

| State | Token | Notes |
|-------|-------|-------|
| Default | `border-stroke-weak` | Structural neutral border (also applied globally via `*`) |
| Prominent | `border-stroke-strong` | Stronger structural border |
| Focus | `focus-visible:border-stroke-focus` | Inputs, interactive elements |
| Active/selected | `border-stroke-selected` | Brand-tinted selection |
| Disabled | `border-stroke-disabled` | Faded structural |
| Semantic | `border-stroke-brand-strong`, `border-stroke-error-strong`, `border-stroke-warning-strong`, `border-stroke-success-strong`, `border-stroke-info-strong` | 80% alpha |
| Semantic soft | `border-stroke-*-weak` | 20% alpha for subtle outlined alerts |

- Use the `stroke-*` tokens for all of `border-*`, `ring-*`, `outline-*`, and `divide-*` utilities — they share the alpha-tuned values.
- Avoid opacity modifiers on `border-stroke-weak` for hover emphasis — switch to `border-stroke-strong` instead.

### Touch feedback

- Every tappable surface that is reachable on the mobile terminal must show press feedback, not only hover: use `TOUCH_PRESS_CLASS` (`active:bg-fill-weak`) or `TOUCH_PRESS_FADE_CLASS` (`active:opacity-60`) from `@/components/ui/touch-press`. Hover-only styling (`hover:*`, `min-[1001px]:hover:*`) is invisible on touch screens.
- Disclosure cards (`MobileDisclosureHeader`) keep their tinted `bg-market-close-card` header over the `bg-surface` card body; the press tint overlays the header through the full-card button. Keep that two-tone structure unless a design decision changes it.

### Dashboard page gutters

- On phones a dashboard page uses one of two surfaces. **Inset panels**: the `DASHBOARD_FRAMES` entry keeps a mobile side padding (`px-4`, or `px-5` for the legal pages) and panels keep their radius and shadow, as on Portfolio, Earn, Staking, Vaults, Referrals and the history pages. **One flat sheet**: the frame has no mobile side padding, the page renders a single full-width `bg-surface` sheet that pads its own content, and the sheet takes its radius only on desktop (`!isMobile && "… rounded-24"`), as on Leaderboard, Funding Comparison and API Wallet. The flat sheet may keep its shadow class; it is square on phones and fills the width, so it does not read as a card.
- Never press a rounded panel against the screen edges: its corners read as a card that lost its margin. `dashboard-frame-view.test.tsx` reads the side padding that applies on phones (a `max-[…]:px-*` override wins over `px-*`, and `px-0` counts as none) and fails when a frame without one is not one of the flat sheets, or when a flat sheet's base class, the `cn()` argument before `!isMobile`, contains a radius. It checks source strings, not computed styles.
- A mobile card that loses width to the gutter must still show its content in full: stack a label above its value, or let a short label or code wrap, instead of truncating addresses, amounts, names, codes or labels (see the Vault cards with `tests/browser/vaults-list.pw.ts`, and the referral code and step labels with `tests/browser/referral-code-card.pw.ts`). A wrapped label that would leave one character on its own line takes `text-balance`.
- Dashboard pages share three corner sizes. A page surface on the dashboard canvas is `rounded-24` (12px) with `shadow-raised` (the API wallet's page-scoped shadow has the same value), on desktop and as a phone inset panel; a flat phone sheet takes the same `rounded-24` only on desktop. Cards, sections, notices and card-shaped placeholders inside a surface are `rounded-16` (8px), and a box nested in a card is never rounder than the card. Controls (inputs, selects, segmented filters, buttons) and shared `@sairn/ui` primitives keep their own radius. Portfolio embeds the Trade page's phone account cards; they carry `data-account-card` and Portfolio's container rounds them to 8px, so the Trade page keeps its own 14px cards. `dashboard-surface-radius-contract.test.ts` reads every non-dialog component of the dashboard pages: a page surface must be `rounded-24` with a shadow, every other radius must be `rounded-16` (or `rounded-t-16` for a card header) unless the class string is on its listed control exceptions, and class names must be plain double-quoted strings.
- Deliberate exceptions to those corners: the Trade page's phone account cards keep the 14px of the mobile trade handoff (Portfolio rounds its embedded copies to 8px through `data-account-card`), the API wallet's own inputs, selects and buttons keep the handoff's `rounded-20`, and the Market Close / funds family keeps its handoff cards. A new exception needs a reason in the contract test's list.
- A single-column mobile grid gets an explicit `grid-cols-1` track. Without it the implicit column grows to the widest `nowrap` content inside a card (a long name, a link) and an `overflow-hidden` panel clips the card without any page overflow to notice; browser checks compare each card with its column's content box, on both sides so right-to-left layouts are covered.

### Dialog transitions

- `Modal` and `Drawer` from `@sairn/ui` gate an initially-open mount so Base UI still runs the enter transition; do not bypass them with `Dialog.Root` directly for app dialogs.
- Never add `!transition-none` or `data-starting-style:*` / `data-ending-style:*` overrides to `AdaptiveModal` `className` / `overlayClassName`; the 200 ms slide (drawer) and fade + scale (modal) are the contract. Destructive action buttons may keep `!transition-none` for their colors.
- Store-driven global modals must derive `open` from the store (never a literal `open`), because the host keeps a closing modal mounted for 250 ms so its exit transition can run.
- A dialog that owns a store session (for example Market Close) closes with `onOpenChange(false)` → local closing state → `onOpenChangeComplete(false)` → release the session, so the exit animation finishes before the component unmounts.
- A dialog that loads lazily from a surface holding unsent input (the order form) uses `createRetryableLazyComponent` and is mounted through `LazyDialogHost` from `@/components/ui/lazy-dialog-host`; never `createLazyComponent`, which reloads the page on a missing chunk and would discard the draft. Warm such dialogs on intent (pointer, press or focus reaching the surface), not on an idle timer: a download every load performs is startup weight (`docs/terminal-performance-baseline.md`).
- A dialog kept mounted through its exit (via `useLingeringValue` or a local closing state) must treat `open === false` as cancelled: disable its confirm/submit control with `!open` and early-return in the handler, and invalidate any pending async work it owns. A closing dialog must never submit.

### Menu popups

- Two tiers only. **Navigation and form menus** (header `More`, account, language, the utilities popover, order-type and other trading-panel dropdowns) use the shared skin from `@/lib/ui/menu-popup-skin`: `menuPopupSkinClass` for action menus whose items stay `text-fg` (and keep `text-error` for destructive entries), `menuPopupSelectionSkinClass` for pick-one menus (muted options, selected option on `bg-trading-panel-card` in bold), `menuPopupSurfaceClass` for a `Popover` that only needs the surface. **Dense in-table filters and order-book controls** keep the `@sairn/ui` `Dropdown` default.
- The shared skin is `rounded-24` (12px) with `p-1`, `bg-overlay`, `shadow-overlay` and `border-trading-panel-stroke-card`; items are `rounded-16` (8px), `px-3 py-2`, `text-2sm` medium, 34px tall on desktop and `min-h-11` with `text-sm` at `max-[1000px]`; disabled entries use `text-fg-disabled`. A menu takes the font of the region that opens it, so every skinned menu is `font-market-close`.
- Call sites add only what is content-specific (width, `max-h`, icon size, hiding the check icon). Do not restyle a skinned menu with `!` modifiers, arbitrary radii or a one-off shadow or disabled colour; `modal-surface-contract` fails on those.
- Overrides work without `!` because `cn()` knows the project scales. Both merge helpers (`@/lib/cn`, `packages/ui/src/utils.ts`) list the numeric radius scale and named shadows, and the terminal helper also lists `font-market-close`; `class-merge-theme-scales.test.ts` fails when a theme key is added without listing it. Without that entry, tailwind-merge keeps both the primitive class and the override and the stylesheet order decides which one wins.

### Dialog chrome

- The `@sairn/ui` primitives own dialog chrome: a centered `ModalPopup` is `rounded-32` (16px) with `border border-stroke-weak`, `bg-modal` and `shadow-overlay`; a bottom `Drawer` is `rounded-t-32` with the same border. In the dark terminal `bg-modal` equals the page colour, so the border is the dialog's edge; do not remove it on desktop.
- A dialog that flattens its phone sheet scopes that to the sheet: `max-[1000px]:!border-0`, never an unscoped `!border-0`.
- A dialog that can be dismissed always offers an explicit, focusable way out on the phone sheet: the close button, or a Cancel / Back / Close button in its body. The drawer handle is decoration (`aria-hidden`, not a control), and swipe, scrim tap and Esc are shortcuts, not the exit: with the keyboard open the scrim can be fully covered, and a screen reader cannot reach any of them. Hide the close button only while an action is pending. A `showClose` that depends on the layout, or is `false`, must be registered with its explicit exit in `dialog-dismiss-control-contract.test.ts`. Do not put a second label in a sheet header where the close button belongs.
- The Deposit / Withdraw / Bridge dialog does not scroll as a whole. `FundsModalShell` clips the popup, keeps the header with its close and back buttons fixed, and scrolls only the body (the form's own visible heading is part of the body and scrolls with it), with the scrollbar hidden (`[scrollbar-width:none] [&::-webkit-scrollbar]:hidden`, as `hidden-horizontal-scrollbar-contract` does for horizontal strips). The desktop modal and the phone sheet get the same structure from the one shell. Content is sized to fit common viewports (1363×852 and 393×852 in `tests/browser/account-actions.pw.ts`); a shorter phone scrolls the body without a visible bar and without losing the close button. The status and wrong-network screens of the same dialog are separate `AdaptiveModal` instances and do not use this structure yet. `funds-modal-scroll-contract` pins the classes; the browser test scrolls the body with the wheel, compares the close button's position before and after, and checks that the popup itself never scrolls.
- Do not pass a smaller named radius (`rounded-t-16`, `min-[1001px]:rounded-16`) to `AdaptiveModal`; take the primitive default. The remaining off-scale sheet radii (`!rounded-t-[18px]`, `!rounded-t-[20px]`) and `min-[1001px]:!rounded-[16px]` come from the market-close design handoff and are pinned by its tests; replacing them needs a design decision because 18px and 20px are not on the named scale.

### Dialog content blocks

- Content inside a dialog uses three tiers, never a stack of grey boxes: a **key/value row** is plain text (`flex items-center justify-between text-xs`, label `text-fg-muted`, value `text-fg`), or an `InfoRowGroup` with dividers when there are several; a **notice** is a semantic callout (`rounded-16 border border-stroke-info-weak bg-info-soft text-info`, or the `success` / `warning` / `error` family) with its icon in the matching `text-icon-*`; a **card that carries an action or a control** is outlined on the dialog surface (`rounded-16 border border-stroke-weak p-3`, no fill).
- `bg-fill-weak` / `bg-fill-weaker` are interactive fills for hover, press, chips, badges, segmented pills and skeletons; do not use them as the background of static content panels. Warning and error callouts use `border-stroke-*-weak`, never an opacity modifier on the strong stroke.
- The Market Close / funds family keeps its handoff cards (`bg-market-close-card` / `bg-trading-panel-card` with `rounded-[10px]`); this rule covers the shared `@sairn/ui` dialogs and application modals that do not follow that handoff.
- Every notice inside a dialog is `rounded-16`, and so is the shared `@sairn/ui` `Alert`, which pages use for the same purpose. `dialog-notice-radius-contract.test.ts` reads every component whose file name says dialog, drawer or sheet or that renders a dialog primitive (`AdaptiveModal`, `Modal`, `Drawer`), treats all string arguments of one `cn()` call as one class list, and checks the `Alert` primitive; a notice with no radius class of its own is not detected, so give every notice an explicit radius; the trading dialog notices that predate this rule are listed there as pending exceptions until a design decision, and fixing one means removing it from that list.

### Loading placeholders

- A placeholder never redraws the layout of the content it stands in for. A hand-copied skeleton is a second copy of that layout, and nothing fails when the content is redesigned: the deposit dialog's chunk fallback kept a six-block form at a fixed 600px for six weeks after the form itself had changed twice. Use one of three forms instead: a blank `aria-busy` region with a screen-reader-only label (`PassiveDataPlaceholder`, a `min-h-*` block inside the real page surface), a neutral spinner for a lazy dialog chunk, or the real component rendered with placeholder values.
- When a placeholder must hold geometry, it takes that geometry from the same source as the content: a shared CSS variable (`--orderbook-row-height`), a shared class constant (`UNIT_DEPOSIT_INFO_LIST_CLASS`), or the real content's shape rendered `invisible` (the funding address placeholder holds an invisible 42-character address and a copy-sized spacer in the ready field, and `tests/browser/account-actions.pw.ts` compares the two heights). Never a second literal height, column layout or card class, and never only a shared class name: content decides the height too.
- A lazy dialog's chunk fallback is one of two things. Either it claims no chrome of the dialog it stands in for, like the shared `LazyDialogLoadingFallback` (margin, leverage, account mode) and `GlobalModalLoadingFallback` (the other global modals), or it renders the same shell component as the loaded dialog. The Deposit / Withdraw / Bridge dialog is the one dialog of the second kind: it and its fallback both render `FundsModalShell`, on every deposit path. Do not copy a dialog's `className` strings into a fallback.
- The deposit dialog is warmed on intent so its fallback is the rare case: every control that opens it spreads `depositModalIntentProps` (pointer enter, press, focus) from `lazy-global-modals` onto that control, not onto a container, and only while the control can open the dialog. `warmDepositModal` imports the module itself, so a failed warm-up never reaches the lazy component. The onboarding gate opens the dialog without a control and cannot warm it.
- Generic pulsing bars that claim no layout may stay for list pages. `loading-placeholder-contract.test.ts` registers every file that uses `animate-pulse` with its count and reason, pins the deposit dialog and its fallback to one shell and the fallback to a spinner and its label, and registers per file how many calls open the deposit dialog and how many controls warm it. It reads source text: a static grey block without `animate-pulse` outside the deposit fallback is not detected, and the open and warm counts do not prove which element carries the warm-up or that its condition is true, so review a new loading state or deposit entry against this section. `deposit-modal-warm.test.ts` runs the real lazy component through a failed warm-up. `global-modals-hip3-disclaimer.test.tsx` renders the deposit fallback and pins its content to the label and the spinner.

### Checking a visual rule

- Write a visual rule in this guide and pin it with a contract test in the same change. The test lists every exception with its reason and expected count, fails when a listed exception is no longer used, and must fail against the code before the fix: check it by mutating a fixed class, not only by reading the test. Never let the size of a radius decide whether something counts as a control.
- Cover every place the rule renders, not only the default route: disconnected and connected-with-data states (a fixture when no account is available), loading, empty and error states, the dialogs a page opens, and components a page embeds from another surface.
- Measure rendered styles as well as class strings. `apps/terminal/tests/browser/dashboard-surface-audit.mjs <origin>` prints the computed radius of every dashboard surface, card and notice by nesting depth at 1440px and 375px against a running dev server, and works while the in-app browser pane is hidden. Report it as a script reading, not a visual review, and name the states it did not reach.
- A rule left partly unenforced, or an exception that waits for a decision, goes into the contract's pending list and the task record's follow-ups, never only into a reply.

### Button states

- A filled button moves through its state tokens (`bg-action` → `bg-action-hover` → `bg-action-active`); never add `hover:opacity-*` or `active:opacity-*` on top. In the dark theme `--action-hover` is brighter than `--action`, so fading the element cancels the hover and dims the label with it.
- Guard hover and press with `not-data-disabled` so a disabled button cannot take a hover fill by stylesheet order, and list every property a state changes (`scale` for the press) in the `transition-[…]` list or it snaps.
- A resting fill and its hover fill must resolve to different values in both themes: `--fill-weak` and `--fill-hover` are both 6% white in the dark theme, so a `bg-fill-weak` button hovers to `bg-fill-press`. `connect-cta-state-contract` pins this for the Connect buttons.
